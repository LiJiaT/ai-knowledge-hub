简介

Chisel 设计虽是高层参数化的，但现有验证流程需先编译为低层 Verilog/SystemVerilog 并实例化参数，导致每个位宽需单独验证，而算术单元的形式验证复杂度又随位宽指数增长。论文提出将算术 Chisel 设计自动转换为保留高层特性的 Scala 仿真程序，再用 Scala 演绎验证工具 Stainless 生成验证条件并由 SMT solver 证明，从而一次性证明设计对所有位宽正确；转换以约 4500 行的 Scala 编译器插件实现，将位向量建模为有界数学整数，用 Trans/Run 函数与依赖重排序建模时序与组合语义。针对非线性计算导致的证明卡顿，作者提出不变量提供、DSL 手工证明与引理归纳等证明精化策略，并沉淀 ghost variables、位向量库（6 操作/10 引理/320 行）与列表库（7 操作/3 引理/140 行）。案例上成功验证了 RocketChip 与 XiangShan 中的 2 个除法器与 2 个乘法器，转换代码膨胀最多 2.3×，多数案例人工证明代价 1.8-2.9×，显著低于 Kami 的 11× 以上。论文自述为 proof-of-concept，目前仅支持可正确转换的 Chisel 子集且子模块限组合电路。

问题

Chisel 设计本身是高层参数化的，但现有验证流程需先编译生成低层 Verilog/SystemVerilog（参数被实例化、Bundle/Vec 等高层结构被展平），导致一个参数化设计必须按每个位宽分别编译、分别验证；同时算术单元（乘法器/除法器）的低层形式验证受位宽带来的状态爆炸困扰，验证复杂度随位宽指数增长。论文要解决的问题是：对参数化算术 Chisel 设计进行高层形式验证，使其正确性一次性对所有位宽成立，而非逐位宽单独验证。

方法

提出 Chisel→Scala 的自动转换（实现为约 4500 行 Scala 代码的 Scala 编译器插件 chicala），将算术 Chisel 设计转换为模拟其行为的 Scala 程序并保留高层特性，再用 Scala 演绎验证工具 Stainless 生成验证条件（VC）并交由 SMT solver 证明。关键技术包括：(1) 将 Chisel 的 UInt/SInt/Bool/Bundle/Vec 建模为 Scala 类型，位向量建模为有界数学整数（BigInt 值+位宽），以支持参数化位宽与算术性质证明；(2) 用 Trans 函数建模单周期组合行为、用递归函数 Run 模拟时钟节拍并以 setTimeout 控制验证终止条件；(3) 基于依赖分析与拓扑排序对 connect 语句重排序，正确建模 Chisel 的并行连接语义与 last-connect-wins 原则；(4) 针对非线性算术性质导致的证明卡顿，提出证明精化策略（为 Run/Trans 提供不变量作为前置/后置条件、用 Stainless DSL 手工证明、定义并归纳证明引理）与证明技术（ghost variables、位向量引理库、列表引理库）。

关键结果

成功对 RocketChip 与 XiangShan 两个开源 RISC-V 处理器中的 2 个除法器（shift/subtract 算法）与 2 个乘法器（XiangShan: Booth 编码+Wallace-Tree；RocketChip: shift/add）完成全位宽一次性形式正确性验证

转换不引起代码规模爆炸：生成 Scala 代码相对 Chisel/Verilog(64-bit) 代码最多膨胀 2.3×

除 X-multiplier 外，各案例人工证明代价轻量（#Scala-vrf 与 #Scala 之比 1.8-2.9×）；X-multiplier 因数据结构与算法更复杂，证明代价显著更高

对比 Kami（其证明代码/实现代码行数比超过 11），本方法证明代价低得多

沉淀位向量库（6 个操作、10 条引理、共 320 行 Scala）与列表库（7 个操作、3 条引理、共 140 行 Scala）

自动转换插件约 4500 行 Scala 代码，以 Scala 编译器插件形式实现并开源（chicala）

创新点

据作者所述，这是首次对 Chisel 硬件设计实现高层参数化形式验证。与既有面向固定位宽低层设计的验证方法（BDD、计算机代数、定理证明器）不同，本方法无需逐位宽验证；与基于证明助手的参数化 HDL（如 Kami）不同，本方法直接验证既有 Chisel 设计而无需重写实现，且验证大部分自动化、代价显著更低；与 RRL 只验证底层算法不同，本方法验证实际硬件设计；与 ChiselTest 等官方流程先实例化参数再验证不同，本方法保持位宽参数进行验证。

ABSTRACT

Chisel 是一种嵌入在 Scala 中的开源硬件描述语言，旨在便于进行参数化和可复用的数字电路设计。Chisel 正日益流行，已被用于设计 RISC-V CPU，例如 RocketChip 和 XiangShan。尽管 Chisel 具有高层次硬件设计的特点，但其验证仍然停留在低层次：首先从 Chisel 程序生成低层次（例如 Verilog）程序，然后将验证工具应用于这些低层次程序。在本工作中，我们关注算术单元的形式化验证。由于位宽带来的状态爆炸问题，算术单元的高效低层次形式化验证一直是一项挑战，并且仍然是一个活跃的研究领域。为了在算术 Chisel 设计中规避这一问题，我们提出了一种对其进行高层次形式化验证的方法，从而一次性地验证其在所有位宽下的正确性，而不是针对每个位宽分别进行验证。其关键思想是将算术 Chisel 设计转换为能够模拟其行为的 Scala 软件程序，同时保留其高层次特性，然后借助 Stainless——一种面向 Scala 的演绎式形式化验证工具——进行验证。我们通过形式化验证两个具有代表性的开源 RISC-V 处理器（即 RocketChip 和 XiangShan）中除法器和乘法器的正确性，验证了该方法的有效性。与现有的基于证明辅助工具的算术设计参数化验证方法（例如 Kami）相比，我们方法的验证成本平均而言要低得多。

KEYWORDS

Chisel、乘法器与除法器、Scala、形式化验证、证明精化。

在本工作中，我们主张释放高层语言 Chisel 的力量：Chisel 中的算术设计最好与高层验证相配合。我们的目标是一次性地形式化验证参数化算术 Chisel 设计在所有位宽下的正确性，而不是对每个位宽分别验证一次。为实现这一目标，我们面临以下两个挑战。

算术单元是处理器中最关键的部分之一。对速度、功耗和面积效率的需求使得算术单元，尤其是其中的乘法器和除法器，变得复杂因而容易出错。对算术单元进行形式化验证是必要的。目前，一旦 Chisel 设计完成，它就会被向下编译并生成 Verilog/SystemVerilog 程序。随后便可以应用现成的 Verilog/SystemVerilog 验证工具。与 Chisel 程序相比，Verilog/SystemVerilog 程序是低层的：当从 Chisel 程序生成 Verilog/SystemVerilog 程序时，参数（例如位宽）被实例化，高层数据结构（例如 bundle 和向量）全部被展平。因此，尽管 Chisel 硬件设计是高层的，其验证却仍然是低层的。具体到算术单元，通过 Verilog/SystemVerilog 进行的低层验证意味着，即使参数化的 Chisel 设计是面向所有位宽的单一设计，它也必须被编译为多个相互独立的 Verilog/SystemVerilog 程序，每个位宽对应一个，并且每个程序都必须分别进行验证。

贡献。我们通过提出一种针对参数化算术 Chisel 设计的高层形式化验证方法来应对上述挑战。具体而言，我们做出了以下贡献。

据我们所知，这是首次针对 Chisel 硬件设计实现高层参数化形式化验证。

相关工作。人们已经为算术电路设计的形式化验证做出了许多努力，尤其是针对乘法器和除法器，例如采用二叉决策图（BDD）[5, 6, 10, 17]、计算机代数 [15, 16, 20, 22, 23] 以及定理证明器 [25, 26] 等方法。这些工作聚焦于具有固定位宽的低层设计，必须对每个位宽分别进行验证，其验证复杂度随位宽呈指数增长。相比之下，我们的方法面向高层参数化算术 Chisel 设计，能够一次性对所有位宽进行形式化验证。

至于 Chisel 设计，目前 Chisel 的官方验证工具是 ChiselTest [19]。它包含形式化验证与仿真功能 [11, 12]，并支持更具表达力的断言 [27, 29, 34]。然而，所有这些工作都会先将 Chisel 设计编译为低层设计并实例化参数，然后再应用验证技术。我们的工作则提出保持在高层，保留算术 Chisel 设计的位宽参数，并一次性对所有位宽进行验证。我们从 Chisel 到 Scala 的转换可以看作 [21] 中从 Verilog 到 C 的转换的扩展。与 Verilog 到 C 的转换相比，Chisel 的高层特性（例如 bundle 和递归函数）使得转换复杂得多。

[4, 9, 13] 也考虑了参数化验证。这些工作提出了基于证明助手的专用硬件描述语言（HDL）。参数化电路设计可以用这些 HDL 来描述，在证明助手中进行形式化验证，甚至可以自动综合为低层电路。然而，我们的动机是验证用 Chisel 编写的现有算术设计，而不是重新实现它们。因此，这些方法并不直接适用于我们的场景。此外，这些基于证明助手的方法中的形式化验证在很大程度上依赖人工，而我们的方法则大部分是自动化的。因此，我们方法的验证工作量要低得多（关于该比较的更多细节见第 4 节）。人们还利用定理证明器 Rewrite Rule Laboratory（RRL）[14] 研究了自动化的参数化验证。我们的方法与 RRL 的主要区别在于：我们的方法验证的是实际的算术硬件设计，而 RRL 仅验证底层算法。

组织结构。第 2 节致力于将 Chisel 硬件程序转换为 Scala 软件程序。第 3 节展示如何使用 Stainless 证明由算术 Chisel 设计生成的 Scala 软件程序的正确性。第 4 节描述案例研究。第 5 节总结本文。

2 TRANSFORMING CHISEL TO SCALA

转换算法解决了 Chisel 硬件生成器与 Scala 电路模拟器之间的语义差异。我们使用清单 1 中的 Chisel 程序来说明这一转换。该程序以 len 作为参数，len 为其输入 in（第 3 行）和输出 out（第 4 行）的位宽。核心寄存器 R 在第一个时钟周期结束时获得 io.in 的值（第 10 行）。然后在之后的每个时钟周期中，它都会向右循环移位 1 位（第 13 行）。因此，再经过 len 个时钟周期后，state 再次变为 true，cnt 等于 len，而 R 重新获得 io.in 的值。例如，若 len 为 4 且 io.in 为 1001，则在第一个时钟周期结束时，R 取值为 1001（此时 cnt 为 0）；在第二个时钟周期中，𝑅 的第 0 位（即 1）被拼接到 100 的左侧，因此在该时钟周期结束时，𝑅 取值为 1100（此时 cnt 为 1）。此后，它分别在第 3、第 4 和第 5 个时钟周期结束时取值为 0110、0011 和 1001。

2.1 Chisel Types and Operations

Chisel 嵌入在 Scala 中。一个 Chisel 程序通常同时包含 Chisel 类型和 Scala 类型。为了将 Chisel 程序转换为 Scala，需要用 Scala 类型对 Chisel 类型进行建模。

Chisel 提供了诸如 UInt、SInt 和 Bool 之类的基本类型，更复杂的类型（例如 Bundle 和 Vec）可以在这些基本类型之上构建。硬件信号（例如 Reg、Wire 和 IO）由这些类型构造而成。我们定义了 Scala 类型 UInt、SInt 和 Bool 来建模相应的 Chisel 基本类型，并用 Scala 变量表示 Chisel 中的所有硬件信号。例如，Chisel 类型为 UInt 的硬件信号 in（清单 1 第 3 行）由清单 2 所示的生成的 Scala 程序中 Scala 类型为 UInt 的 Scala 变量 io_in（第 1 行）建模。具体而言，位向量类的 Chisel 类型由有界数学整数建模。以 UInt 为例。Scala 的 UInt 包含两个字段：一个类型为 BigInt 的数学整数值 value 及其位宽 width。前者是位向量的无符号解释，后者限制了 value 的取值范围。之所以采用这种方式而不是直接用位向量来建模 Chisel 的 UInt，原因有二。首先，由于我们面向的是参数化的 Chisel 设计，其中的大多数位向量具有参数化的位宽；然而，我们的验证后端 Stainless 不支持这种参数化位宽的位向量。其次，由于我们关注的是算术电路，数学整数比位向量更适合用于证明算术性质。需要注意的是，将位向量建模为有界数学整数仍然是准确的。

与 Chisel 基本类型相关联的操作，例如布尔运算、算术运算和按位运算，也由我们为 Scala 类型定义的操作来建模（例如清单 1 第 13 行的 Chisel 拼接操作 Cat 变为清单 2 第 16 行的 Scala Cat）。此外，Chisel 中的连接操作（:=）被转换为我们定义的 Scala 中的连接操作（:=），其行为类似于赋值，但会按照 Chisel 语义额外进行位宽计算。最后，Chisel 的控制流 when - otherwise 由 Scala 中的 if - else 建模。

2.2 Modeling Sequential Circuits

Chisel 提供了类型 Reg 来定义寄存器并构建时序电路。在 Chisel 程序中，全局时钟信号被隐式地连接到寄存器。因此，一个（时序）Chisel 设计被转换为一个名为 Trans 的 Scala 函数（清单 2 中第 5 行），该函数描述单个时钟周期内的组合逻辑行为，以及一个模拟时钟节拍的循环。Trans 函数接受输入和寄存器的状态，并生成输出和寄存器的新状态。这些寄存器的新状态将在下一个时钟周期成为当前的寄存器状态。为了模拟时钟周期内寄存器更新的正确行为，我们为每个寄存器引入两个 Scala 变量：一个表示当前状态（例如清单 2 中第 10 行的 R），另一个表示下一状态（例如清单 2 中第 10 行的 R_next）。表示下一状态的 Scala 变量用表示当前状态的变量进行初始化（清单 2 中第 8-10 行）。如果相应的寄存器被连接到新的对象，这些变量就会被更新。例如，R 在清单 1 的第 13 行被连接，因此 R_next 在清单 2 的第 16 行被更新。

模拟时钟节拍的循环被实现为递归函数 Run（清单 2 中第 23 行）。由于算术电路通常在经过若干个时钟周期的计算后才产生输出，递归函数 Run 的调用次数由用户定义的函数 setTimeout（清单 2 中第 25-26 行）控制，该次数由我们想要验证的程序性质决定。例如，在清单 2 中，超时条件被设置为 newRegs.cnt.value == len。Scala 函数 Init（清单 2 中第 27 行）将寄存器初始化与函数 Run 结合起来，从而忠实地对原始 Chisel 程序进行建模。

2.3 Modeling Combinational Behaviors by Reordering Statements

尽管在生成电路时 Chisel 程序是按顺序读取的，但为了理解电路在一个时钟周期内的组合行为，电路中 connect 语句的执行——因而原始 Chisel 程序中 connect 语句的执行——除“最后连接生效”（last-connect-wins）原则外，应被视为并行的。例如，在清单 1 中，connect 语句并行执行以更新信号的值，例如 state、cnt 和 R。因此，Chisel 程序中 connect 语句的并行执行与 Scala 程序中赋值语句的顺序执行之间存在不匹配。因此，我们必须在 Chisel 程序的转换过程中对语句进行重排序，使得生成的 Scala 程序能够正确模拟原始 Chisel 程序的行为。

语句之间的依赖关系是依据其中的 Chisel 硬件信号和 Scala 变量建立的。随后基于依赖关系的拓扑序执行重排序。具体而言，依赖关系存在于以下四种情形中。(i) 根据 Chisel 的“最后连接生效”（last-connect-wins）原则，如果对同一硬件信号存在多个连接，则最后一个连接生效。这与 Scala 程序的顺序执行语义一致。因此，对同一信号的每个连接都依赖于前一个连接，使得最后一个连接保持在末尾。(ii) 硬件信号需要先被计算再被使用。因此，使用某个信号的语句依赖于该信号的最后一次连接。(iii) 所有硬件信号和 Scala 变量应保持定义、赋值和引用之间的相对顺序。(iv) when-otherwise 块或 if-else 块内的语句应遵循分支条件所涉及的硬件信号或 Scala 变量的依赖关系。

我们根据语句之间的依赖关系对 Chisel 程序中的语句进行重排序。例如在清单 1 中，io.ready 在第 9 行被用作 when 的条件，但它是在第 16 行被连接的。因此，when 块中的所有语句都依赖于第 16 行的语句。基于这些依赖关系，我们相应地对这些语句进行重排序。这样，语句 io_ready := regs.state（清单 2 中的第 11 行）被放置在由 when 生成的 if 语句（第 12 行）之前。

对于 Chisel 程序中的函数调用，我们在这些函数的函数体内独立地进行重排序。对于子模块的实例化，我们采用与函数调用类似的方式处理，但只允许组合电路类型的子模块。此外，为了获得更灵活的语句重排序，我们将一个 when - otherwise 或 if - else 块拆分为多个块，使得每个块只包含一条语句。例如，清单 1 中包含 5 条语句的 when - otherwise 块（第 9-15 行）被拆分为 5 个块。第 1 个块是 when(io.ready){R := io.in}，第 4 个块是 when(io.ready){}. otherwise{cnt := cnt + 1.U}。为了在转换过程中尽可能保留给定 Chisel 程序的结构，我们将由 Chisel 的 when - otherwise 语句生成的那些 Scala 语句进行合并，前提是它们在重排序后是相邻的。清单 2 中的 if - else 块（第 12-19 行）就是通过这种合并方式由 when - otherwise 块生成的。

3 FORMAL VERIFICATION OF SCALA PROGRAMS

Stainless 是一个针对 Scala 中一个表达能力丰富的子集的验证工具。它提供 require 和 ensuring 关键字来编写前置条件和后置条件，生成验证条件（VCs），并利用 SMT 求解器对其加以证明。若所有生成的 VC 均被证明，则验证成功。它还提供了一种领域特定语言，供用户在 SMT 求解器无法证明 VC 时借助提示来引导证明。

给定由我们的转换（第 2 节）所生成的 Scala 程序，我们按如下方式进行验证过程。

例如，我们在第 2 节中已经推导出，代码清单 1 中参数化 Chisel 程序里的寄存器 R 在 cnt 等于 len 时等于 io.in。如果我们想要验证这一属性，终止条件应当为 cnt == len。因此在第一步中，我们将 setTimeout 中的终止条件指定为 newRegs.cnt.value == len。Init 的后置条件被指定为 ensuring(Regs.R.value == ins.io_in.value)。至于前置条件，我们要求位宽满足 len > 1，并使用 require 关键字加以定义。然后在第二步中，调用 Stainless 来验证该 Scala 程序。

在第二步中应用 Stainless 通常并不像按一下按钮那样简单。由于由算术 Chisel 设计生成的 Scala 程序是参数化的，并且通常涉及非线性计算，使用 Stainless 进行的验证常常会陷入停滞。这需要人工投入来引导或精化证明。我们根据经验提出了一些证明精化策略和证明技术，以帮助 Stainless 顺利完成证明过程。

策略陷入停滞。当某个策略（例如 trivial）的检查陷入停滞时，我们需要添加引理和/或对证明进行精化。例如，Listing 4 中的证明在第 2 行陷入停滞，在该行我们利用性质 2 𝑥 · 2 𝑦 = 2 𝑥 + 𝑦 将 Pow2(w-c-1) * Pow2(c) 等同于 Pow2(w-1)。这一步无法被“平凡地”（trivially）证明，因为 Stainless 无法自动推导出该性质。因此，我们将该性质定义为一个引理 Pow2Mul，并通过归纳法对其进行证明。我们用该引理 Pow2Mul 的实例化替换有问题的 trivial，此后这一步的证明即可顺利通过。

4 IMPLEMENTATION AND CASE STUDIES

We implemented our transformation as a plugin of the Scala compiler 1 . The plugin converts the Scala abstract syntax tree (AST) into a special AST, then applies the passes including preprocessing, dependency analysis, and statement reordering, and finally generates Scala code as input to Stainless. The automatic transformation plugin comprises approximately 4500 lines of Scala code.

We have successfully applied our approach to verify the correctness of Chisel designs for integer division and multiplication in open-source RISC-V processors XiangShan and RocketChip, for all bit widths at once. Both divider designs are based on the classic, widely-used shift/subtract algorithm: one is from the Radix2Divider module [32] in the XiangShan project, the other is from the RocketChip project [2]. 5 CONCLUSION AND FUTURE WORK

我们提出了一种新颖的方法来验证算术 Chisel 设计的正确性，该方法可以一次性验证所有位宽，而无需对每个位宽分别验证一次。我们的方法基于将算术 Chisel 设计自动转换为 Scala 程序，并结合 Stainless（一种针对 Scala 的演绎验证工具），以及一些专门针对算术设计的证明细化策略和证明技术。这项工作是 Chisel 硬件设计高层验证的一个概念验证。我们希望这项工作能够激发这一方向的更多研究。

作为未来工作，首先，我们希望在更多的算术 Chisel 设计上验证该方法。此外，从 Chisel 程序到 Scala 程序的自动转换能否得到改进和扩展，以便于对更复杂的 Chisel 硬件设计进行高层（不一定是形式化的）验证，也是一个有趣的问题。最后，我们计划通过运行 Chisel 和 Scala 代码并比较其结果，对从 Chisel 到 Scala 的转换进行实证验证。
