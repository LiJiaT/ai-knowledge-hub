简介

论文针对开源 LLM（如 LLaMA）工具调用能力显著弱于 ChatGPT 等闭源模型的问题，提出涵盖数据构建、模型训练与评测的通用工具使用框架 ToolLLM。方法上，作者用 ChatGPT 自动构建 ToolBench 指令微调数据集：从 RapidAPI 采集并过滤出 16,464 个真实 RESTful API，生成单工具与多工具两类指令，并用新提出的 DFSDT（基于深度优先搜索的决策树）标注解法路径，克服 CoT/ReACT 错误传播与探索受限的缺陷；同时训练神经 API 检索器为指令推荐相关 API，并构建自动评测器 ToolEval（pass rate 与 win rate，与人工一致性分别达 87.1% 和 80.3%）。基于 ToolBench 微调 LLaMA-2 得到 ToolLLaMA，性能与 ChatGPT 相当，可零样本泛化到分布外数据集 APIBench，且检索器推荐的 top-5 API 甚至优于 ground-truth API 集。对团队而言，这是工具调用数据构建、Agent 搜索策略与工具使用评测方法的重要参考。

问题

开源 LLM（如 LLaMA）虽经指令微调具备通用对话能力，但在工具使用（调用外部 API 完成人类指令）上显著落后于 ChatGPT 等 SOTA 闭源模型，原因是现有指令微调数据集中于基础语言任务、忽视工具使用领域；同时缺乏覆盖大规模真实 API、含多工具多步场景的训练数据，以及可靠的工具使用自动评测手段。

方法

三阶段自动构建 ToolBench 数据集：(1) 从 RapidAPI Hub 采集 API 及其文档元数据（名称、描述、参数、示例响应等）并严格过滤；(2) 通过采样 API 组合 + ChatGPT（配人工编写的 in-context seed examples）生成多样化单工具/多工具指令及 (instruction, relevant API) 对；(3) 用 DFSDT 搜索可行解法路径——将多步决策构建为决策树，允许模型评估多条推理路径、调用 'Finish by Giving Up' 放弃当前节点并扩展新节点，缓解 CoT/ReACT 的错误传播与探索受限。另训练基于 Sentence-BERT 的 API 检索器（对比学习），构建 ToolEval 自动评测器（pass rate/win rate，LLM 评审多次预测多数投票），并用 ToolBench 微调 LLaMA-2 7B（positional interpolation 将上下文扩到 8192）得到 ToolLLaMA；推理时 API 响应超 1024 tokens 则按 ChatGPT 学到的压缩策略裁剪。

创新点

ABSTRACT

尽管开源大语言模型（LLMs）（如 LLaMA）取得了长足进展，但它们在工具调用能力方面仍存在显著局限，即利用外部工具（API）来完成人类指令的能力。其原因在于，当前的指令微调主要聚焦于基础语言任务，而忽视了工具调用领域。这与最先进的（SOTA）闭源 LLMs（如 ChatGPT）出色的工具调用能力形成了鲜明对比。为弥合这一差距，我们提出了 ToolLLM——一个涵盖数据构建、模型训练与评估的通用工具调用框架。我们首先提出 ToolBench，一个面向工具调用的指令微调数据集，该数据集使用 ChatGPT 自动构建。具体而言，构建过程可分为三个阶段：(i) API 收集：我们从 RapidAPI Hub 收集了 16,464 个涵盖 49 个类别的真实 RESTful API；(ii) 指令生成：我们提示 ChatGPT 生成涉及这些 API 的多样化指令，覆盖单工具与多工具两种场景；(iii) 解答路径标注：我们使用 ChatGPT 为每条指令搜索有效的解答路径（API 调用链）。为增强 LLMs 的推理能力，我们开发了一种新颖的基于深度优先搜索的决策树算法。它使 LLMs 能够评估多条推理轨迹并扩展搜索空间。此外，为评估 LLMs 的工具调用能力，我们开发了一个自动评估器：ToolEval。基于 ToolBench，我们对 LLaMA 进行微调，得到一个 LLM——ToolLLaMA，并为其配备一个神经 API 检索器，以便为每条指令推荐合适的 API。实验表明，ToolLLaMA 在执行复杂指令和泛化到未见过的 API 方面展现出卓越能力，并取得了与 ChatGPT 相当的性能。我们的 ToolLLaMA 在一个分布外的工具调用数据集 APIBench 上也展现出强大的零样本泛化能力。代码、训练好的模型和演示已公开发布于 https://github.com/OpenBMB/ToolBench 。

2 DATASET CONSTRUCTION

我们介绍 ToolBench 的三阶段构建流程：API 收集（§ 2.1）、指令生成（§ 2.2）以及解决方案路径标注（§ 2.3）。所有流程均基于 ChatGPT（ gpt-3.5-turbo-16k ），仅需极少的人工监督，并且可以轻松扩展到新的 API。

2.1 API COLLECTION

We start by introducing RapidAPI and its hierarchy, followed by how we crawl and filter APIs.

RapidAPI Hub RapidAPI is a leading API marketplace that connects developers with thousands of real-world APIs, streamlining the process of integrating diverse services into applications. Developers can test and connect with various APIs by registering only a RapidAPI key. All APIs in RapidAPI can be classified into 49 coarse-grained categories (link), such as sports, finance, and weather. The categories associate an API with the most relevant topic. Additionally, the hub also provides 500+ fine-grained categorization called collections (link), e.g., Chinese APIs and database APIs. APIs in the same collection share a common characteristic and often have similar functionalities or goals.

Hierarchy of RapidAPI As shown in Figure 3, each tool may be composed of multiple APIs. For each tool, we crawl the following information: the name and description of the tool, the URL of the host, and all the available APIs belonging to the tool; for each API, we record its name, description, HTTP method, required parameters, optional parameters, request body, executable code snippets for API call, and an example API call response. This rich and detailed metadata serves as a valuable resource for LLMs to understand and effectively use the APIs, even in a zero-shot manner.

API Filtering Initially, we gathered 10 , 853 tools ( 53 , 190 APIs) from RapidAPI. However, the quality and reliability of these APIs can vary significantly. In particular, some APIs may not be well-maintained, such as returning 404 errors or other internal errors. To this end, we perform a rigorous filtering process (details in appendix A.1) to ensure that the ultimate tool set of ToolBench is reliable and functional. Finally, we only retain 3 , 451 high-quality tools ( 16 , 464 APIs).

2.2 INSTRUCTION GENERATION

与以往工作不同，我们特别关注指令生成的两个关键方面：（1）多样性：训练大语言模型（LLM）处理广泛的 API 使用场景，从而提升其泛化能力和鲁棒性；（2）多工具使用：反映现实世界中经常需要多个工具相互配合的情况，提高 LLM 的实际适用性和灵活性。为此，我们并非从零开始凭空构思指令然后再搜索相关 API，而是采样不同的 API 组合，并精心设计涉及这些 API 的各类指令。

为 API 生成指令　将 API 总集合定义为 S API，每次我们从 S API 中采样若干个 API：S sub N = { API 1 , · · · , APIN }。我们提示 ChatGPT 理解这些 API 的功能，然后生成（1）涉及 S sub N 中 API 的可能指令（Inst ∗），以及（2）每条指令（Inst ∗）的相关 API（S rel ∗ ⊂ S sub N），即 { [ S rel 1 , Inst 1 ] , · · · , [ S rel N ′ , InstN ′ ] }，其中 N ′ 表示生成实例的数量。这些（指令，相关 API）对将用于训练 § 3.1 中的 API 检索器。我们使用不同的采样策略（稍后介绍）来覆盖所有 API 及其大部分组合，从而确保指令的多样性。

ChatGPT 的提示由以下部分组成：（1）对预期指令生成任务的总体描述；（2）S sub N 中每个 API 的完整文档，帮助 ChatGPT 理解它们的功能及相互配合方式；（3）三个上下文种子示例 { seed 1 , seed 2 , seed 3 }。每个种子示例都是由人类专家撰写的理想指令生成结果。我们利用这些种子示例，通过上下文学习（in-context learning）来更好地规范 ChatGPT 的行为。我们总共为单工具 / 多工具设置编写了 12 / 36 个多样化的种子示例（S seed），并在每次随机采样三个示例。指令生成的详细提示见附录 A.7。总体而言，生成过程可以表述如下：

2.3 SOLUTION PATH ANNOTATION

如图 4 所示，给定一条指令 Inst∗，我们提示 ChatGPT 搜索一个有效的动作序列：{a_1, · · · , a_N}。这样一个多步决策过程被转化为 ChatGPT 的多轮对话。在每一轮 t 中，模型基于先前的交互生成一个动作 a_t，即 ChatGPT(a_t |{a_1, r_1, · · · , a_{t-1}, r_{t-1}}, Inst∗)，其中 r∗ 表示真实的 API 响应。对于每个 a_t，ChatGPT 需要指明其“思考”（thought）、要使用哪个 API 以及该 API 的具体参数，即 a_t 具有如下格式：'Thought: · · · , API Name: · · · , Parameters: · · ·'。

为了利用 ChatGPT 的函数调用（function call）特性，我们将每个 API 视为一个特殊函数，并将其 API 文档填入 ChatGPT 的函数字段中。这样，模型便能理解如何调用该 API。对于每条指令 Inst∗，我们将所有采样得到的 API S_sub_N 作为可用函数输入给 ChatGPT。为了让 ChatGPT 完成整个动作序列，我们定义了两个额外的函数，即 'Finish with Final Answer' 和 'Finish by Giving Up'。前一个函数带有一个参数，该参数对应于针对原始指令的详细最终答案；而后一个函数则是为如下情况设计的：在多次 API 调用尝试之后，所提供的 API 仍无法完成原始指令。

**基于深度优先搜索的决策树** 在我们的初步研究中，我们发现思维链（CoT）(Wei et al., 2023) 或 ReACT (Yao et al., 2022) 存在固有的局限性：(1) 错误传播：一个错误的动作可能进一步传播错误，并使模型陷入错误的循环，例如以错误的方式持续调用某个 API 或产生幻觉 API；(2) 探索受限：CoT 或 ReACT 只探索一个可能的方向，导致对整个动作空间的探索有限。因此，即使是 GPT-4 也常常无法找到有效的解题路径，使得标注变得困难。

为此，我们提出构建一棵决策树来扩展搜索空间，并提高找到有效路径的可能性。如图 4 所示，我们的 DFSDT 允许模型评估不同的推理路径，并选择：(1) 沿着一条有希望的路径继续推进，或 (2) 通过调用 'Finish by Giving Up' 函数放弃现有节点，并扩展一个新节点。在节点扩展过程中，为了使子节点多样化并扩展搜索空间，我们将先前生成的节点的信息作为提示提供给 ChatGPT，并明确鼓励模型生成一个不同的节点。在搜索过程中，我们倾向于采用深度优先搜索（DFS）而非广度优先搜索（BFS），因为只要找到一条有效路径即可完成标注。而使用 BFS 将耗费过多的 OpenAI API 调用。更多细节在附录 A.8 中描述。我们对所有生成的指令执行 DFSDT，并仅保留那些成功通过的解题路径。最终，我们生成了 126,486 个（指令，解题路径）对，用于在 § 3.2 中训练 ToolLLaMA。

3 EXPERIMENTS

在本节中，我们研究 ToolLLM 框架的性能。我们首先在 § 3.1 中介绍评估指标，并评估 API 检索器（API retriever）和 DFSDT 的有效性。然后在 § 3.2 中展示主要实验，随后在 § 3.3 中进行泛化实验。

3.1 PRELIMINARY EXPERIMENTS

ToolEval 考虑到 RapidAPI 上 API 的时间变异性，以及一条指令可能存在无穷多种潜在解决路径，为每条测试指令标注固定的标准答案（ground-truth）解决路径是不可行的。此外，在比较不同模型时，确保它们在评估过程中使用相同版本的 API 至关重要。考虑到人工评估可能十分耗时，我们参照 AlpacaEval (Li et al., 2023b)，基于 ChatGPT 开发了一个高效的评估器 ToolEval，它包含两个评估指标（详见附录 A.5）：（1）通过率（Pass Rate）：它计算在有限预算内成功完成一条指令的比例。该指标衡量大语言模型（LLM）执行指令的可执行性，可视为理想工具调用的基本要求；（2）胜率（Win Rate）：我们向 ChatGPT 评估器提供一条指令和两条解决路径，并获取其偏好（即哪一条更好）。我们为这两个指标预先定义了一组评判标准，并将这些标准组织为 ChatGPT 评估器的提示（prompt）。我们基于 ChatGPT 进行多次评估以提高可靠性，然后计算评估器给出的结果的平均值。

通过严格的测试（详见附录 A.5），我们发现 ToolEval 与人工标注者在通过率上达到了 87.1% 的高度一致性，在胜率上达到了 80.3% 的一致性。这表明 ToolEval 在很大程度上能够反映并代表人工评估。

4 RELATED WORK

工具学习（Tool Learning）　近期研究揭示了大语言模型（LLM）在掌握工具以及在复杂环境中进行决策方面蓬勃发展的能力 (Vemprala et al., 2023; Nakano et al., 2021; Qin et al., 2023a; Shen et al., 2023; Wu et al., 2023; Schick et al., 2023; Hao et al., 2023; Qian et al., 2023; Song et al., 2023; Zhuang et al., 2023; Gao et al., 2023)。获取外部工具赋予 LLM 实时的事实知识 (Yang et al., 2023)、多模态功能 (Gupta & Kembhavi, 2023) 以及垂直领域的专业技能 (Jin et al., 2023)。然而，开源 LLM 在工具调用方面仍远远落后于最先进（SOTA）LLM，且 SOTA LLM 究竟如何习得工具调用能力仍不清楚。在本文中，我们旨在弥合这一差距，并深入探究其底层机制。

指令微调（Instruction Tuning）　指令微调可增强 LLM 理解人类指令并生成恰当回复的能力 (Wei et al., 2021; Bach et al., 2022; Mishra et al., 2022)。由于人工标注指令微调数据十分耗时，self-instruct (Wang et al., 2022) 提出利用 SOTA LLM 生成高质量数据，这助推了近期面向多轮对话的数据整理趋势 (Taori et al., 2023; Chiang et al., 2023; Xu et al., 2023a; Penedo et al., 2023; Ding et al., 2023)。然而，与对话相比，鉴于 API 的巨大多样性以及多工具指令的复杂性，工具学习本质上更具挑战性。因此，即使是 GPT-4 也常常无法找到有效的解决方案路径。然而，现有的工具学习数据集 (Li et al., 2023a; Patil et al., 2023; Tang et al., 2023; Xu et al., 2023b) 及其构建方法无法有效应对 § 1 中提到的真实人类需求。相比之下，我们的 ToolBench 面向实际场景而设计，并改进了以往的工具学习数据构建流程。

面向决策的大语言模型提示　提示使大语言模型（LLMs）能够将高层任务分解为子任务，并生成有依据的计划 (Ahn et al., 2022; Huang et al., 2022a;b; Ye et al., 2023)。ReACT (Yao et al., 2022) 将推理与行动相结合，允许 LLM 为某个行动给出恰当的理由，并将环境反馈纳入推理过程。然而，这些研究并未纳入决策撤回机制，这会带来问题，因为一个初始错误可能导致后续错误的级联。最近，Reflexion (Shinn et al., 2023) 通过要求 LLM 对先前的失败进行反思来缓解这一问题。我们的 DFSDT 通过允许 LLM 评估不同的推理路径并选择最有希望的一条，将 Reflexion 扩展为一种更通用的方法。值得注意的是，DFSDT 与一项同期工作——思维树（ToT）推理 (Yao et al., 2023)——有着相似的思想。然而，我们的 DFSDT 面向的是决策空间为无限的通用决策问题，而 ToT 针对的是可通过暴力搜索解决的相对简单任务，例如 24 点游戏（Game of 24）和填字游戏（Crosswords）。DFSDT 与 ToT 在目标上的差异决定了二者在实现细节上的显著不同。

5 CONCLUSION

在本工作中，我们介绍了如何激发大语言模型（LLM）内在的工具调用能力。我们首先提出了一个指令微调数据集 ToolBench，它涵盖 16000+ 个真实世界的 API 以及多种实际使用场景，包括单工具与多工具任务。ToolBench 的构建完全使用 ChatGPT，仅需极少的人工监督。此外，我们提出 DFSDT 以增强 LLM 的规划与推理能力，使其能够策略性地在推理路径中进行导航。为了高效地评估工具学习，我们设计了一个自动评估器 ToolEval。通过在 ToolBench 上微调 LLaMA，所得到的模型 ToolLLaMA 达到了与 ChatGPT 相当的性能，并对未见过的 API 展现出出色的泛化能力。另外，我们开发了一个神经网络 API 检索器，用于为每条指令推荐相关的 API。该检索器可与 ToolLLaMA 集成，构成更加自动化的工具调用流水线。在实验中，我们展示了该流水线对分布外领域的泛化能力。总体而言，本工作为指令微调与 LLM 工具调用交叉领域的未来研究铺平了道路。

A.1 DETAILS FOR FILTERING RAPIDAPI

我们执行了严格的筛选流程，以确保 ToolBench 最终的工具集可靠且功能正常。筛选流程如下：(1) 初步测试：我们首先测试每个 API 的基本功能，以确认其是否可正常运行。我们舍弃任何不满足这一基本标准的 API；(2) 示例响应评估：我们调用 API 以获取示例响应，然后根据响应时间和质量来评估其有效性。持续表现出较长响应时间的 API 会被剔除。此外，我们还过滤掉响应质量低下的 API，例如返回 HTML 源代码或其他错误信息的 API。

A.2 API RESPONSE COMPRESSION

在检查每个 API 返回的响应时，我们发现某些响应可能包含冗余信息，且长度过长，无法直接输入大语言模型（LLMs）。由于 LLMs 的上下文长度有限，这可能引发问题。因此，我们执行响应压缩，在保留关键信息的同时缩短 API 响应的长度。

由于每个 API 的响应格式是固定的，我们使用 ChatGPT 分析一个响应示例，并移除响应中不重要的键（keys）以缩短其长度。针对每个 API，ChatGPT 的提示（prompt）包含以下信息：(1) 工具文档，包括工具名称、工具描述、API 名称、API 描述、参数以及一个示例 API 响应。这为 ChatGPT 提供了关于该 API 功能的线索；(2) 3 个上下文学习（in-context learning）示例，每个示例包含一个原始 API 响应和一个由专家撰写的压缩后响应模式。通过这种方式，我们得到了所有 API 的响应压缩策略。在推理阶段，当 API 响应长度超过 1024 个 token 时，我们通过移除不重要的信息来压缩响应。如果压缩后的响应仍长于 1024，我们仅保留前 1024 个 token。通过人工评估，我们发现这种压缩保留了 API 响应中包含的重要信息，并成功去除了噪声。

A.3 DETAILS FOR TRAINING TOOLLLAMA

我们以多轮对话模式训练模型。在训练数据格式方面，我们保持输入和输出与 ChatGPT 的相同。由于尚不清楚 ChatGPT 如何组织函数调用字段，我们只是将这些信息拼接进输入中，作为 ToolLLaMA 提示的一部分。在训练超参数方面，我们使用 5 × 10 - 5 的学习率、4 × 10 - 2 的预热比例、64 的总批量大小、8192 的最大序列长度，并使用 2 的位置插值比例。我们对模型进行两个 epoch 的训练，并选择在开发集上表现最佳的模型检查点，然后在测试集上进行评估。

A.4 DETAILS FOR DFSDT

在实践中，在有效性与成本（即 OpenAI API 调用次数）之间取得平衡至关重要。经典的深度优先搜索（DFS）算法在每一步生成多个子节点，然后对所有子节点进行排序，并选择得分最高的节点进行扩展。在贪心地扩展至终端节点后，DFS 会回溯以探索附近的节点，从而扩大搜索空间。在整个算法过程中，最消耗资源的部分是子节点的排序过程。如果我们使用大语言模型（LLM）每次评估两个节点，则需要大约 O ( n log n ) 复杂度的 OpenAI API 调用，其中 n 为子节点的数量。
