ProjDevBench: Benchmarking AI Coding Agents on End-to-End Project Development

ProjDevBench：面向端到端项目开发的 AI Coding Agent 基准评测

简介

现有 coding agent 评测多停留在函数级代码生成或已有代码库的 issue 修复，无法反映 agent 从自然语言需求出发独立构建完整可运行项目的能力。论文提出 ProjDevBench，从 OJ 平台约 2800 道候选题中筛出 20 个跨 8 类别的项目级任务，要求 agent 从零或基于不完整代码库构建含多源文件与 CMake 构建配置的完整仓库，并采用 Online Judge 加权执行评分（80%）加 LLM 与规则混合代码审查（20%）的双轨评测协议。对 6 个 agent 框架搭配多个前沿模型的评测显示整体通过率仅 27.38%，Codex+GPT-5 以 77.85 分居首，失败集中在规格理解偏差、边界条件、时间复杂度优化与资源管理。交互轮数与 token 消耗和最终分数呈强负相关（Spearman ρ=-0.668/-0.734），说明当前 agent 难以把长交互转化为有效进展。LLM 代码审查与人类判断一致性高（accuracy 0.852、Cohen's κ 0.710），可作为可扩展的规格合规评估手段。

问题

现有 coding agent 基准（HumanEval、MBPP 为函数级，SWE-bench、RepoBench 为已有仓库的补丁修复）多采用单次生成与二元 pass/fail 反馈，无法评估 agent 从高层自然语言规格出发端到端构建完整、可执行、多文件软件项目的能力，也缺乏细粒度失败诊断与规格级合规检查。

方法

构建端到端项目开发基准：经范围过滤与质量过滤三阶段流程精选 20 个项目级任务，分为 project-creation（从零构建，Hard）与 project-completion（补全不完整代码库，Easy）两种设定，要求 agent 产出含多源文件、CMake 构建配置且可编译运行的 Git 仓库（人类参考解平均约十个源文件）。评测采用双轨协议：Online Judge 加权执行评分，提供 compile error、runtime error、TLE、MLE、wrong answer 等细粒度诊断信号；代码审查结合规则脚本（检查禁用库等显式违规）与 LLM 评审（判断作弊解法、测试套件漏洞利用等规格级合规）。最终分数按执行 80% + 审查 20% 加权。在统一 prompt 下评测 Cursor、GitHub Copilot、Claude Code、Augment、Codex CLI、Gemini CLI 六个 agent 框架，搭配 GPT-5、Claude Sonnet 4.5、Gemini 3 Pro Preview 及 GLM-4.6、Kimi-k2-0905-Preview、DeepSeek-V3.2-Exp 等开源模型，并对失败模式与交互长度做系统归因分析。

关键结果

整体提交通过率仅 27.38%，其中 41.86% 因 Wrong Answer 失败、13.91% 因超出时间限制失败

Codex+GPT-5 取得最高最终加权分 77.85，优于 Augment+GPT-5（72.35）、Cursor+GPT-5（71.85）、Claude Code+Sonnet-4.5（68.87）；Cursor+Gemini-3-Pro-Preview 达 75.32

从零构建的 hard 任务上框架鲁棒性差异放大：Codex+GPT-5 执行分从 easy 的 79.24 降至 69.22，而 GitHub Copilot+Sonnet-4.5 从 71.10 骤降至 36.63，Gemini CLI 从 74.57 降至 35.53

Claude Code 框架下开源模型 GLM-4.6、Kimi-k2-0905-Preview、DeepSeek-V3.2-Exp 最终分为 57.95、52.77、50.33，均落后于 Sonnet-4.5 的 68.87

任务平均需要 138 个交互轮次与 4.81M tokens，最复杂任务需长达两小时；交互轮数、token 消耗与最终分数呈强负相关（Spearman ρ=-0.668 与 -0.734），轮数与 token 消耗强正相关（0.898）

LLM 代码审查与人类判断高度一致：二元规则校验 accuracy 0.852、Cohen's κ 0.710

代码审查揭示执行评测无法发现的问题：agent 本地 commit 但未 push 到远端、构建配置错误、使用禁用头文件或 using namespace std、遗漏必需文件、修改受保护模板等

创新点

与 HumanEval/MBPP（函数级）、SWE-bench/RepoBench（已有仓库补丁修复）、DevEval（分阶段提供 UML 等参考材料、不要求完全自主构建）、E2EDevBench/NL2Repo-Bench（窄领域、二元反馈）不同，ProjDevBench 要求从高层规格（或无初始代码）端到端构建完整可执行仓库，并将 OJ 细粒度诊断信号（错误类型分类与部分得分）与 LLM+规则代码审查结合为加权双轨评分，同时系统分析交互长度与性能的相关性，这是现有基准未覆盖的。
