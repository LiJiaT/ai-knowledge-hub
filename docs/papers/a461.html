简介

论文针对开发者与 ChatGPT 等对话式 LLM 协作时提示知识零散、难以复用的问题，借鉴软件设计模式思想提出 prompt pattern（提示模式）概念及文档化框架。方法上，采用 Intent and Context、Motivation、Structure and Key Ideas（以 fundamental contextual statements 自然语言语句描述结构）、Example Implementation、Consequences 的模式形式，整理出 16 个模式，划分为 Input Semantics、Output Customization、Error Identification、Prompt Improvement、Interaction、Context Control 等类别，如 Persona、Flipped Interaction、Fact Check List、Template、Context Manager 等，并演示多模式组合的用法。关键结论是：提示工程可以像软件模式一样被命名、编目、复用与组合，从而更可靠地约束输出格式、自动化输出步骤并进行事实核查。论文未做量化评测，所有示例均在 ChatGPT（ChatGPT+ 服务）上人工验证。对团队而言，这是提示词资产化与模式化管理的奠基性参考。

问题

用户与对话式 LLM 交互时，提示知识以零散示例形式存在，缺乏系统化、可复用、可组合的工程化方法来约束输出、自动化流程并保证输出质量。论文要为提示工程建立类似软件设计模式的文档化框架与模式目录，使提示解决方案可被结构化描述、分类、复用并跨领域迁移，尤其面向自动化软件开发任务。

方法

将软件模式形式移植到提示工程：定义 prompt pattern 的文档结构（Intent and Context、Motivation、Structure and Key Ideas、Example Implementation、Consequences），其中模式结构用 fundamental contextual statements（自然语言关键语句）而非形式文法描述；给出 16 个模式的目录，分为 Input Semantics（Meta Language Creation）、Output Customization（Output Automater、Persona、Visualization Generator、Recipe、Template）、Error Identification（Fact Check List、Reflection）、Prompt Improvement（Question Refinement、Alternative Approaches、Cognitive Verifier、Refusal Breaker）、Interaction（Flipped Interaction、Game Play、Infinite Generation）与 Context Control（Context Manager）；并说明模式可组合使用（如 Game Play+Persona、Question Refinement+Cognitive Verifier+Fact Check List）。所有示例在 ChatGPT（ChatGPT+）上验证。

区别于此前只研究具体提示词效果的工作，本文的核心贡献是将软件设计模式的形式系统化引入提示工程：提出 prompt pattern 概念与文档框架，提供可命名、分类、复用与组合的 16 个模式目录，并用 fundamental contextual statements 替代 UML 或形式文法来描述模式结构。论文自述其与已有研究互补之处在于 'providing a structure for documenting, discussing, and reasoning about prompts'，即帮助用户建立结构化提示的心智模型，而非聚焦个别提示示例。

摘要——提示工程是与 ChatGPT 等大语言模型（LLMs）进行有效对话所需的一项日益重要的技能集。提示是给予 LLM 的指令，用于强制执行规则、实现流程自动化，并确保所生成输出的特定质量（和数量）。提示也是一种编程形式，可用于定制与 LLM 的输出和交互。

本文描述了一个以模式形式呈现的提示工程技术目录，这些技术已被应用于解决与 LLM 对话时的常见问题。提示模式是一种类似于软件模式的知识传递方法，因为它们为在特定情境（即使用 LLM 时的输出生成与交互）下面临的常见问题提供了可复用的解决方案。

本文为将 LLM 应用于自动化软件开发任务的提示工程研究做出了以下贡献。首先，本文提供了一个框架，用于记录通过结构化提示来解决一系列问题的模式，从而使这些模式能够适配到不同领域。其次，本文给出了一个已被成功应用于改进 LLM 对话输出的模式目录。第三，本文解释了如何由多个模式构建提示，并举例说明了一些与其他提示模式组合后能够受益的提示模式。

I. INTRODUCTION

以 ChatGPT [2] 为代表的对话式大语言模型（Large Language Model，LLM）[1] 在众多领域引发了极大关注，其应用任务涵盖从回答医师执照考试题目 [3] 到生成代码片段等多个方面。本文聚焦于增强 LLM 在若干领域中的应用，例如帮助开发者借助不熟悉的 API 高效且有效地编写代码，或帮助学生掌握新的编程技能与技术。

在人类与 AI 工具作为可信赖的协作者协同工作、以更快速且更可靠地演化依赖软件的系统 [4] 的领域中，LLM 尤其具有前景。例如，LLM 正被直接集成到诸如 Github 的 Co-Pilot [5]-[7] 等软件工具中，并被纳入 IntelliJ [8] 和 Visual Studio Code 等集成开发环境（IDE）中，从而使软件团队能够直接从其偏好的 IDE 访问这些工具。

提示（prompt）[9] 是提供给 LLM 的一组指令，它通过定制 LLM 和/或增强或改进其能力来对 LLM 进行编程。提示可以通过为 LLM 对话提供一组初始规则和具体的规则与准则，来影响后续与 LLM 的交互以及由 LLM 生成的输出。具体而言，提示为对话设定上下文，并告知 LLM 哪些信息是重要的，以及期望的输出形式和内容应当是什么。

例如，提示可以规定 LLM 只生成遵循某种编码风格或编程范式的代码。同样，提示也可以规定 LLM 在生成的文档中标记出某些关键词或短语，并提供与这些关键词相关的附加信息。通过引入这些准则，提示能够促成更加结构化且更为细致的输出，从而在 LLM 的应用背景下辅助各种各样的软件工程任务。

提示工程是通过提示对 LLM 进行编程的手段。为了展示提示工程的威力，我们给出如下提示：

提示：“从现在开始，我希望你向我提问，以便将一个 Python 应用程序部署到 AWS。当你掌握了足够的信息来部署该应用程序时，请创建一个 Python 脚本来自动完成部署。”

这个示例提示会使 ChatGPT 开始就用户的软件应用程序向用户提问。ChatGPT 将主导这一提问过程，直到它掌握了足够的信息来生成一个能够自动化部署的 Python 脚本为止。该示例展示了提示在编程方面的潜力，其能力超越了传统的“生成一个实现 X 的方法”式提示或“回答这道测验题”式提示。

此外，还可以对提示词（prompt）进行工程化设计，以对 LLM 进行编程，使其完成的任务远不止简单地指定输出类型或过滤提供给模型的信息。借助合适的提示词，可以创建全新的交互范式，例如让 LLM 生成并给出与某个软件工程概念或工具相关的小测验，甚至模拟一个 Linux 终端窗口。此外，提示词还具有自适应的潜力，可以建议其他提示词来收集更多信息或生成相关产物。提示词的这些高级能力凸显了对其进行工程化设计的重要性，从而提供超越简单文本或代码生成的价值。

提示模式（prompt pattern）对于有效的提示工程至关重要。本文的一个关键贡献是引入提示模式，用以记录在与对话式 LLM 交互时系统地工程化不同输出目标和交互目标的成功方法。我们主要关注与领域无关的提示模式的工程化，并介绍了一个基本提示模式目录，用于解决从生成可视化和代码产物，到自动化有助于对输出进行事实核查的输出步骤等各类问题。

B. Overview of Prompt Patterns

提示模式（prompt pattern）与软件模式类似，都为特定问题提供可复用的解决方案。然而，它们更具体地聚焦于从诸如 ChatGPT 这样的大规模语言模型（LLMs）生成输出的语境。正如软件模式为解决常见的软件开发挑战提供了成文化的方法，提示模式也为定制 LLM 的输出与交互提供了成文化的方法。

在自动化软件开发任务的场景下，通过文档化并利用提示模式，个人用户和团队可以对生成的输出施加约束，确保相关信息被包含在内，并改变与 LLM 交互的格式，从而更好地解决他们所面临的问题。提示模式可以被视为庞大的通用软件模式体系的一个推论，只是将其适配到了 LLM 输出生成这一更具体的语境中。

D. A Way Forward: Fundamental Contextual Statements

因此，一个开放的研究问题是：在描述提示模式的结构与思想方面，何种方法比形式文法更为有效。我们提出了基本上下文语句（fundamental contextual statements）的概念，即对提示中需要向大语言模型（LLM）传达的重要思想的书面描述。一个思想可以根据用户的需要和经验以任意方式重写和表达。然而，需要传达的关键思想会以一系列简单但根本性的语句形式呈现给用户。

采用并应用基本上下文语句方法的一个好处是，它被有意设计得对用户直观易懂。具体而言，我们期望用户能够理解如何以适合其领域上下文的方式来表达和调整这些语句。此外，由于提示的底层思想已被捕获，用户可以用替代的符号或措辞来表达这些相同的思想，而这些符号或措辞是通过模式引入 LLM 的，例如第 III-B 节中介绍的元语言创建（Meta Language Creation）模式。

我们的最终目标是通过提供一个用于设计提示的框架来增强提示工程，使所设计的提示能够被复用和/或适配到其他 LLM，就像软件模式可以用不同的编程语言和平台来实现一样。不过，就本文而言，所有提示均使用 ChatGPT+ 服务在 ChatGPT [12] 上进行了测试。由于 ChatGPT 具有广泛的可用性和流行度，我们在本文给出的所有示例中均使用 ChatGPT 作为 LLM。这些示例的记录整理结合了两种途径：一是探索互联网上社区发布的提示语料库，二是我们在使用 ChatGPT 自动化软件开发任务的过程中独立创建的提示。

如表中所示，我们的分类框架中共有五类提示模式：Input Semantics（输入语义）、Output Customization（输出定制）、Error Identification（错误识别）、Prompt Improvement（提示改进）和 Interaction（交互），下文将分别对每一类进行概述。

Input Semantics 类别处理 LLM 如何理解输入，以及它如何将输入转换为可用于生成输出的内容。该类别包括 Meta Language Creation（元语言创建）模式，其重点是为 LLM 创建一种可供其理解的自定义语言。当默认输入语言不适合表达用户想要向 LLM 传达的想法时，该模式非常有用。

Output Customization 类别侧重于约束或定制 LLM 所生成输出的类型、格式、结构或其他属性。该类别中的提示模式包括 Output Automater（输出自动化器）、Persona（角色扮演）、Visualization Generator（可视化生成器）、Recipe（配方）和 Template（模板）模式。Output Automater 模式允许用户创建脚本，以自动执行 LLM 输出所建议用户执行的任何任务。Persona 模式为 LLM 赋予一个在生成输出时所扮演的角色。Visualization Generator 模式允许用户通过生成可馈送给其他工具的文本输出来创建可视化，例如其他基于 AI 的图像生成器，如 DALL-E [13]。Recipe 模式允许用户获得一系列步骤或动作，以实现所声明的最终结果，且可能是在信息或约束仅部分已知的情况下。Template 模式允许用户为输出指定一个模板，由 LLM 用内容填充该模板。

Error Identification 类别侧重于识别并解决 LLM 所生成输出中的错误。该类别包括 Fact Check List（事实核查清单）和 Reflection（反思）模式。Fact Check List 模式要求 LLM 生成一份输出所依赖、应当进行事实核查的事实清单。Reflection 模式要求 LLM 对其输出进行自省并识别其中的任何错误。

提示改进（Prompt Improvement）类别侧重于提升输入与输出的质量。该类别包括问题细化（Question Refinement）、替代方法（Alternative Approaches）、认知验证器（Cognitive Verifier）和拒绝破解（Refusal Breaker）这几种模式。问题细化模式确保大语言模型（LLM）始终为用户的问题建议一个更好的版本。替代方法模式要求 LLM 为完成用户指定的任务提出替代方法。认知验证器模式指示 LLM 自动建议一系列子问题供用户回答，然后再将各子问题的答案组合起来，得出针对整体问题的答案。拒绝破解模式要求 LLM 在拒绝生成答案时自动改写用户的问题。

交互（Interaction）类别侧重于用户与 LLM 之间的交互。该类别包括翻转交互（Flipped Interaction）、游戏扮演（Game Play）和无限生成（Infinite Generation）这几种模式。翻转交互模式要求 LLM 提出问题而非生成输出。游戏扮演模式要求 LLM 以游戏的形式生成输出。无限生成模式要求 LLM 持续不断地生成输出，而无需用户每次重新输入生成器提示。

最后，上下文控制（Context Control）类别侧重于控制 LLM 运行时所处的上下文信息。该类别包括上下文管理器（Context Manager）模式，该模式允许用户为 LLM 的输出指定上下文。

该模式的关键结构在于向 LLM 解释一个或多个符号、单词或语句的含义，使其在随后的对话中使用所提供的语义。这种描述可以采用简单翻译的形式，例如 'X' 表示 'Y'。这种描述也可以采用更复杂的形式，即定义一系列命令及其语义，例如 '当我说 X 时，我希望你执行 '。在这种情况下，'X' 从此便与 '执行动作' 的语义绑定在一起。

4) 实现示例：成功使用元语言创建（Meta Language Creation）模式的关键在于开发一种无歧义的记号或速记方式，如下例所示：

'从现在起，每当我输入由 ' → ' 分隔的两个标识符时，我就是在描述一个图。例如，'a → b' 描述的是一个包含节点 'a' 和 'b' 以及二者之间一条边的图。如果我使用 '-[w:2, z:3] → ' 来分隔标识符，则是在为边添加属性，例如权重或标签。'

这个元语言创建模式示例通过定义表示节点和边的约定，建立了一种用于描述图的标准化记号。每当作者输入由 ' → ' 符号分隔的两个标识符时，就表明正在描述一个图。例如，如果作者输入 'a → b'，则表明正在定义一个包含节点 'a' 和 'b' 且二者之间存在一条边的图。这一约定提供了一种清晰而简洁的方式，以书面形式传达图的结构。

此外，该提示还进一步规定，可以使用语法 '-[w:2, z:3] → ' 来提供有关边的附加信息，例如权重或标签。这种记号允许在图的基本结构之外指定附加属性。所指定的属性与两个节点之间的边相关联，可以为图的解释提供重要的上下文。这种用于描述图的标准化记号可以使图结构和属性的传达变得更加容易，因为这些内容若用一系列句子来描述可能并不容易，或者会非常冗长。

5) 后果：尽管该模式为定制用户与 LLM 的交互提供了一种强大的手段，但它也可能在 LLM 内部造成混淆。与清晰定义该语言的语义同等重要的是，还必须确保该语言本身不会引入任何会降低 LLM 性能或准确性的歧义。例如，提示 '每当我用逗号分隔两个事物时，即表示第一个事物先于第二个事物' 很可能带来显著的歧义隐患，并且如果在提示中使用了涉及逗号的标点符号，还可能产生意想不到的语义。

为了展示可能产生混淆的情况，ChatGPT 会向用户发出警告，并且可能无法将某个符号或术语特定地映射到新的含义。例如，如果向 ChatGPT 给出以下提示：

“每当我说 'a' 时，我指的是 Marie Antoinette。”

它会回应称该提示会造成过多混淆，因为 'a' 是一个不定冠词且过于常用，如下所示：

“用 'a' 来指代 Marie Antoinette 可能会引起混淆，因为 'a' 是一个不定冠词，通常用于指代此前未曾提及的名词。使用她的名字 'Marie Antoinette'，或者使用诸如 'she' 或 'her' 之类的代词来指代她，可能会更加清晰。此外，借助上下文来明确你所指的对象，也有助于避免对话中的混淆。”

一般而言，LLM 在其训练所用的数据上会有更好的表现。因此，当存在某种既有记法、但它可能并非该符号的主导含义时，元语言创建（Meta Language Creation）模式可以通过提供上下文来限定该符号的含义范围，从而提高输出的准确性和实用性。例如，符号 ' → ' 在图论和命题逻辑中传达的信息略有不同。因此，陈述 'p → q, q → p' 可能是有意义的，但前提是通过元语言创建提示为 LLM 提供了适当的上下文。

尽管元语言创建是一个强大的模式，但必须谨慎使用，尤其是在描述那些原本难以精确或简洁描述的概念时。因此，这类提示最好在全新的对话会话中使用。在每个对话会话中仅使用一种元语言也可能是一种最佳实践，因为这可以避免随着时间推移而在对话中应用相互冲突或出乎意料的语义。

C. The Output Automater Pattern

1) 意图与上下文：该模式的意图是让 LLM 生成一个脚本或其他自动化产物，以便自动执行 LLM 在其输出中建议采取的任何步骤。其目标是减少实现 LLM 输出建议所需的人工投入。

2) 动机：LLM 的输出通常是供用户遵循的一系列步骤。例如，当要求 LLM 生成一个 Python 配置脚本时，它可能会建议修改若干文件以及对每个文件应做的更改。然而，让用户不断执行 LLM 输出所指示的手动步骤既繁琐又容易出错。

Contextual Statements
Whenever you produce an output that has at least one step to take and the following properties (alternatively, always do this)
Produce an executable artifact of type X that will automate these steps

| 0 |

该模式的第一部分用于确定应当生成自动化的情形。一种简单的方法是声明输出至少包含两个待执行的步骤，并且应当生成一个自动化产物。范围界定由用户自行决定，但这有助于避免在以下情况下生成输出自动化脚本：即运行该输出自动化脚本所耗费的用户精力多于执行输出中给出的原始步骤。该范围可以限定为需要超过一定数量步骤的输出。

该模式的下一部分具体说明了 LLM 为执行自动化而应输出的输出类型。例如，“生成一个 Python 脚本”使 LLM 具体理解如何将一般性步骤转换为 Python 中的等效步骤。自动化产物应当是具体的，并且必须是 LLM 能将其与“自动化一系列步骤”这一动作关联起来的事物。

4) 示例实现：下面展示了将此提示模式应用于 ChatGPT LLM 所生成代码片段的一个示例：

“从现在起，每当你生成跨越多个文件的代码时，请生成一个可运行的 Python 脚本，用于自动创建指定的文件，或对现有文件进行更改以插入所生成的代码。”

该模式在软件工程中尤为有效，因为使用 LLM 的软件工程师的一项常见任务就是随后将输出复制/粘贴到多个文件中。某些工具（如 Copilot）会将有限的代码片段直接插入编码人员正在处理的代码部分，但诸如 ChatGPT 之类的工具并不提供此类功能。这种自动化技巧对于创建用于在终端上运行命令的脚本、自动化云操作或重新组织文件系统上的文件同样有效。

该模式对于任何可由计算机控制的系统而言都是强大的补充。LLM 可以提供应在计算机控制系统上执行的一组步骤，随后可将输出转换为脚本，使控制该系统的计算机自动执行这些步骤。这是让诸如 ChatGPT 之类的 LLM 将质量融入具有已知脚本接口的新型计算系统并对其进行控制的一条直接途径。

5) 后果：该模式在使用上的一个重要注意事项是，自动化产物（automation artifact）必须被具体地定义。如果对如何“自动化”这些步骤没有具体的含义，LLM 往往会声明它“无法自动化事物”，因为这超出了它的能力范围。不过，LLM 通常会接受生成代码的请求，因此目标是指示 LLM 生成可被执行以实现某种自动化的文本/代码。这一含义上的细微区别对于帮助 LLM 消除提示含义的歧义非常重要。

输出自动化器（Output Automater）模式的一个注意事项是，LLM 需要足够的对话上下文，才能生成在目标环境中可正常工作的自动化产物，例如 Mac 计算机与 Windows 计算机上项目的文件系统。当自动化所需的完整上下文都包含在对话之中时，该模式的效果最好，例如，当使用对话从零开始生成一个软件应用，并且对本地文件系统的所有操作都是通过一系列生成的自动化产物来执行，而不是通过 LLM 所不知道的手动操作来执行时。或者，自包含的步骤序列也能很好地工作，例如“如何找到我的 Mac 计算机上打开的端口列表”。

在某些情况下，LLM 可能会生成包含多个步骤的长输出，却不包含自动化产物。这种遗漏可能由多种原因造成，其中包括超出了 LLM 所支持的输出长度限制。针对这种情况，一个简单的变通方法是通过后续提示来提醒 LLM，例如“但是你没有自动化它”，这为 LLM 提供了自动化产物被遗漏、应当被生成的上下文。

在 LLM 演进的当前阶段，输出自动化器模式最适合由能够阅读并理解所生成自动化产物的用户来使用。LLM 会（而且确实会）在其输出中产生不准确之处，因此盲目地接受并执行自动化产物会带来重大风险。尽管该模式可以让用户免于执行某些手动步骤，但它并不能免除用户理解其借助输出所执行的操作的责任。因此，当用户执行自动化脚本时，他们便承担起对结果的责任。

D. The Flipped Interaction Pattern

1) 意图与上下文：你希望 LLM 通过提问来获取其执行某些任务所需的信息。因此，不是由用户来驱动对话，而是你希望由 LLM 来驱动对话，使其聚焦于实现某个特定目标。例如，你可能希望 LLM 给你出一个快速小测验，或者自动提问，直到它获得足够的信息来生成将你的应用程序部署到某个特定云环境的部署脚本。

2) 动机：与其让用户驱动对话，LLM 往往拥有可用于更准确地从用户处获取信息的知识。翻转交互模式的目标是翻转交互流程，让 LLM 向用户提问以实现某个期望的目标。LLM 通常能够更好地选择交互的格式、数量和内容，以确保目标能够更快、更准确地达成，和/或借助用户可能（最初）不具备的知识来达成。

Contextual Statements
I would like you to ask me questions to achieve X
You should ask questions until this condition is met or to achieve this goal (alternatively, forever)
(Optional) ask me the questions one at a time, two at a time, etc.

| 0 |

翻转交互的提示应当始终指明交互的目标。第一条想法（即你希望 LLM 通过提问来实现某个目标）向 LLM 传达了这一目标。同样重要的是，问题应当聚焦于特定的主题或结果。通过提供目标，LLM 能够理解它试图通过交互完成什么，并相应地调整其问题。这种“控制反转”能够实现更聚焦、更高效的交互，因为 LLM 只会提出它认为与实现指定目标相关的问题。

第二条想法为交互应当持续多长时间提供了上下文。翻转交互可以通过诸如“停止提问”之类的回复来终止。然而，更好的做法通常是将交互的范围限定在合理的长度内，或仅限于达成目标所需的程度。这个目标可以出人意料地开放，而 LLM 会通过提问持续朝着目标努力，例如“直到你有足够的信息来生成 Python 脚本”这一示例中的情形。

默认情况下，LLM 很可能在每次迭代中生成多个问题。第三条想法完全是可选的，但可以通过限制（或扩展）LLM 在每个周期生成的问题数量来提升可用性。如果没有指定提问的精确数量/格式，提问将是半随机的，可能导致一次一个问题或一次十个问题。因此，可以对提示进行定制，使其包含每次提出的问题数量、问题的顺序，以及任何其他有助于促进用户交互的格式/排序方面的考虑。

4) 示例实现：下面展示了一个翻转交互的示例提示：

“从现在起，我希望你向我提问，以便将一个 Python 应用程序部署到 AWS。当你拥有足够的信息来部署该应用程序时，创建一个 Python 脚本来自动完成部署。”

总体而言，提示中关于约束条件和所需收集信息的描述越具体，结果就越好。例如，上述示例提示可以提供一个可选的 AWS 服务菜单（如 Lambda、EC2 等），用于部署应用程序。在其他情况下，也可以允许 LLM 对用户未明确做出决定的事项自行做出适当的选择。该提示的一个局限在于，一旦提供了与任务相关的其他上下文信息，可能需要通过试验来调整确切的措辞，才能让 LLM 以最适合任务的问题数量和提问流程来提问，例如是一次提出多个问题还是每次只问一个问题。

5) 后果：设计提示时需要考虑的一个问题是，在终止之前应向 LLM 规定收集哪些信息以及规定到何种程度。在上面的示例中，翻转交互是开放式的，最终生成的产物可能存在显著差异。这种开放性使提示具有通用性和可复用性，但可能会额外提出一些问题，而如果提供更多上下文，这些问题本可以被跳过。

如果事先已知具体需求，最好将其注入提示中，而不是寄希望于 LLM 自行获取所需信息。否则，LLM 将非确定性地决定是向用户询问该信息，还是对合适的取值做出有根据的猜测。

例如，用户可以声明希望将应用程序部署到 Amazon AWS EC2，而不是仅仅说“部署到云上”，从而需要多轮交互来缩小部署目标的范围。初始信息越精确，LLM 就越能利用用户可能愿意回答的有限问题来获取信息，从而改进其输出。

在为翻转交互开发提示时，重要的是要考虑用户的知识水平、参与程度和控制程度。如果目标是以尽可能少的用户交互来完成任务（最小控制），则应明确说明这一点。相反，如果目标是确保用户了解所有关键决策并对其进行确认（最大参与），这一点也应明确说明。同样，如果预期用户知识有限，并且问题应针对其专业水平来设计，那么这一信息也应被精心设计到提示中。

E. The Persona Pattern

1) 意图与背景：在许多情况下，用户希望大语言模型（LLM）的输出始终采取某种观点或视角。例如，让 LLM 像一名安全专家那样进行代码审查可能会很有用。该模式的意图是赋予 LLM 一个“角色设定”（persona），帮助它选择生成哪些类型的输出以及关注哪些细节。

2) 动机：用户可能不知道，为了让 LLM 完成某项给定任务，哪些类型的输出或哪些细节是其需要重点关注的。然而，他们可能知道平时会请什么角色或哪类人来帮助处理这些事情。角色设定（Persona）模式使用户能够在不了解所需输出确切细节的情况下，表达他们需要什么样的帮助。

Contextual Statements
Act as persona X
Provide outputs that persona X would create

| 0 |

第一条语句表达了这样一层意思：LLM 需要扮演某个特定的角色设定，并提供该角色设定会给出的输出。这一角色设定可以通过多种方式来表达，从职位描述、头衔，到虚构人物、历史人物等。该角色设定应当能引出一组与某个广为人知的职位头衔或某类人物等相关联的属性。2

第二个想法——提供角色设定 X 会创建的输出——为定制化提供了机会。例如，一名教师可能会提供种类繁多的不同输出类型，从作业到阅读清单再到讲课内容。如果用户已知输出类型应有更具体的范围，则可以在这条语句中予以说明。

2 但请注意，由于 LLM 底层的隐私与安全规则，与在世人物或被认为有害的人物相关的角色设定可能会被忽略。

4) 示例实现：下面展示了用于代码审查的一个示例实现：

“从现在起，请扮演一名安全审查员。请密切关注我们所查看的任何代码的安全细节。请提供安全审查员针对该代码会给出的输出。”

在这个例子中，LLM 被指示提供“安全审查员”会给出的输出。该提示还进一步铺垫了将对代码进行评估这一情境。最后，用户通过将角色设定进一步限定为与代码相关的输出，对该角色设定进行了细化。

角色设定还可以代表无生命或非人类的实体，例如 Linux 终端、数据库，或某种动物的视角。当使用该模式来表示这些实体时，同时说明你希望输入以何种方式传递给该实体也会很有用，例如“假设我的输入是主人对狗说的话，而你的输出则是狗发出的声音”。下面展示了一个针对非人类实体、使用“假装成为”（pretend to be）措辞的示例提示：

“你将假装成为一台已被攻击者入侵的计算机上的 Linux 终端。当我输入一条命令时，你将输出该 Linux 终端会产生的相应文本。”

该提示旨在模拟一台已被攻击者入侵并通过 Linux 终端进行控制的计算机。该提示规定，用户将向终端输入命令，作为响应，模拟终端将输出真实 Linux 终端会产生的相应文本。该提示在角色设定上更具规定性，它要求 LLM 不仅要充当 Linux 终端，还要进一步扮演一台已被攻击者入侵的计算机。

该角色使 ChatGPT 针对命令生成的输出中包含表明这台计算机曾被黑客入侵的文件和内容。该示例展示了 LLM 如何将其情境感知能力带入角色之中，在本例中，即在其生成的输出中制造出网络攻击的证据。这类角色与游戏扮演（Game Play）模式结合使用时可能非常有效，因为在这种模式下，你希望向用户隐藏输出特征的确切细节（例如，不要通过在提示中明确描述而泄露网络攻击的所作所为）。

5) 影响：采用非人类角色的一个有趣之处在于，LLM 可能会围绕上下文做出一些有趣的假设或产生“幻觉”。互联网上广泛流传的一个示例要求 ChatGPT 扮演 Linux 终端，并产生假如用户在终端中键入相同文本时所会得到的预期输出。诸如 ls -l 之类的命令会为一个虚构的 UNIX 文件系统生成文件列表，其中甚至包含可以对其运行 cat file1.txt 的文件。

在其他示例中，LLM 可能会提示用户提供更多上下文，例如当 ChatGPT 被要求扮演 MySQL 数据库时，它会要求用户提供其假装要查询的表的结构。随后，ChatGPT 便可以生成合成的数据行，例如为一个包含 “name” 和 “job” 列的 “people” 表生成虚构的行。

F. The Question Refinement Pattern

1) 意图与背景：该模式让 LLM 参与到提示工程的过程中。此模式的意图是确保对话式 LLM 总是会建议用户可以提出的、可能比其原始问题更好或更精炼的问题。使用该模式，LLM 可以帮助用户找到应当提出的正确问题，从而得出准确的答案。此外，与用户采用试错式提示相比，LLM 或许能帮助用户以更少的交互次数找到所需信息或实现其目标。

2) 动机：当用户提出一个问题时，他们可能并不是该领域的专家，可能不知道表述该问题的最佳方式，或者不了解有助于表述该问题的额外信息。LLM 通常会说明其提供的答案所存在的局限性，或者请求额外的信息以帮助其生成更准确的答案。LLM 还可能说明其在给出答案时所做的假设。其动机在于，这些额外信息或这组假设可以用来生成更好的提示。与其要求用户消化这些额外信息并据此重新表述其提示，不如让 LLM 直接对提示进行精炼，以纳入这些额外信息。

在上述示例的语境中，LLM 将使用问题精炼（Question Refinement）模式，通过询问或利用关于软件制品以及用于构建它的语言或框架的特定细节来改进与安全相关的问题。例如，如果一位使用 FastAPI 开发 Python Web 应用的开发者向 ChatGPT 提问“我该如何在我的 Web 应用中处理用户身份验证？”，LLM 将考虑到该 Web 应用是用 Python 和 FastAPI 编写的，从而对该问题进行精炼。随后，LLM 会提供一个针对该语言和框架更加具体的问题，例如“在 FastAPI Web 应用中安全地处理用户身份验证以缓解跨站脚本（XSS）、跨站请求伪造（CSRF）和会话劫持等常见安全风险的最佳实践是什么？”

精炼后问题中的额外细节不仅可能让用户意识到他们需要考虑的问题，还可能使 LLM 给出更好的回答。对于软件工程任务，该模式还可以融入有关潜在缺陷、模块化或其他代码质量考量方面的信息。另一种方法是自动精炼问题，使生成的代码清晰地分离关注点或尽量减少对外部库的使用，例如：

每当我提出一个关于如何编写某段代码的问题时，请建议一个更好的问题版本，该版本询问如何以尽量减少我对外部库依赖的方式编写代码。

5) 后果：问题精炼模式有助于弥合用户知识与 LLM 理解之间的差距，从而带来更高效、更准确的交互。该模式的一个风险在于，它倾向于迅速将用户的提问收窄到某个特定领域，从而引导用户走上比实际需要更为有限的探究路径。这种收窄的后果是，用户可能会错过重要的“全局”信息。解决该问题的一种方法是为该模式的提示提供额外的范围限定，例如“不要将我的问题限定在特定的编程语言或框架上。”

克服精炼问题被任意收窄或目标受限的另一种方法是将问题精炼模式与其他模式相结合。特别是，该模式可以与认知验证器（Cognitive Verifier）模式相结合，使 LLM 自动生成一系列能够产生精炼问题的后续问题。例如，在下面的提示中同时应用了问题精炼模式和认知验证器模式，以确保向 LLM 提出更好的问题：

“从现在起，每当我提出一个问题时，请额外提出四个问题，以帮助你生成我原始问题的更好版本。然后，利用我的回答来建议我原始问题的一个更好版本。”

与许多允许 LLM 利用其自身知识生成新问题的模式一样，LLM 可能会在问题中引入用户不熟悉的术语或概念。解决这一问题的一种方法是在提示中加入一条语句，要求 LLM 对其引入问题中的任何不熟悉术语进行解释。对该思路的进一步改进是将 Question Refinement 模式与 Persona 模式相结合，使 LLM 标记出这些术语，并生成假定特定知识水平的定义，例如下面这个示例：

“从现在起，每当我提出一个问题时，请额外提出四个问题，以帮助你生成我原始问题的更好版本。然后，利用我的回答来建议我原始问题的一个更好版本。在后续问题之后，请暂时扮演一个对 AWS 毫无了解的用户，并定义我为了准确回答这些问题所需要了解的任何术语。”

LLM 总是可能产生事实性错误，就像人类一样。该模式的一个风险在于，这些错误会被引入到精炼后的问题中。不过，通过结合 Fact Check List 模式（使用户能够识别可能的不准确之处）和 Reflection 模式（用于解释问题精炼背后的推理），可以缓解这一风险。

H. The Cognitive Verifier Pattern

1) 意图与背景：研究文献已经证实，如果将一个问题细分为若干附加问题，并将这些附加问题所提供的答案组合成对原始问题的整体答案，大语言模型（LLM）往往能够更好地进行推理 [14]。该模式的意图是强制 LLM 始终将问题细分为附加问题，这些附加问题可用于为原始问题提供更好的答案。

Contextual Statements

当你被问到一个问题时，遵循以下规则

生成若干有助于更准确回答该问题的附加问题

将各个问题的答案组合起来，得出针对整体问题的最终答案

第一条语句是生成若干有助于更准确回答原始问题的附加问题。这一步指示 LLM 考虑问题的上下文，并识别可能缺失或不清晰的信息。通过生成附加问题，LLM 可以帮助确保最终答案尽可能完整和准确。这一步还能鼓励用户进行批判性思考，并有助于发现最初可能未被考虑到的新见解或新方法，进而引出更好的后续问题。

第二条语句是将各个问题的答案组合起来，得出针对整体问题的最终答案。这一步旨在确保从各个问题中收集到的所有信息都被纳入最终答案。通过组合答案，LLM 能够针对原始问题给出更全面、更准确的回答。这一步还有助于确保所有相关信息都被考虑在内，并且最终答案不会仅基于任何单一答案。

“当我向你提出一个问题时，生成三个有助于你给出更准确答案的附加问题。当我回答完这三个问题后，将这些答案组合起来，得出针对我原始问题的最终答案。”

提示模式（prompt pattern）的这一具体实例对原始模式进行了细化，即指定 LLM 在响应问题时应生成的附加问题的固定数量。在本例中，该提示规定 ChatGPT 应生成三个有助于对原始问题给出更准确答案的附加问题。具体数量可以基于用户的经验以及其提供后续信息的意愿。对该提示的一种细化是为 LLM 可以假设用户在该领域所具备的知识量提供上下文，以指导附加问题的创建：

“当我向你提出一个问题时，生成三个有助于你给出更准确答案的附加问题。假设我对我们正在讨论的主题知之甚少，请对任何非常识性的术语给出定义。当我回答完这三个问题后，将这些答案组合起来，得出针对我原始问题的最终答案。”

该细化还规定，用户可能对所讨论的主题缺乏深入的理解，这意味着 LLM 应当对任何不属于常识的术语进行定义。这有助于确保后续问题不仅相关且聚焦，而且对于可能不熟悉技术术语或领域特定术语的用户来说也是易于理解的。通过提供清晰简洁的定义，LLM 可以帮助确保后续问题易于理解，并确保最终答案对于具有不同知识水平和专业背景的用户来说都是可以理解的。

5) 后果：该模式可以规定要生成的问题的确切数量，也可以将这一决定留给 LLM。规定确切数量各有利弊。利在于，指定问题的确切数量可以严格限定用户被迫提供的附加信息量，使其处于用户愿意且能够贡献的范围之内。

然而，弊在于，给定 N 个问题时，可能存在一个极具价值的第 N+1 个问题，而它总是会被排除在范围之外。另一种做法是为 LLM 提供一个数量范围，或允许其提出额外的问题。当然，如果不对问题数量加以限制，LLM 可能会生成大量额外的问题，从而使用户不堪重负。

该模式示例增加了一个限定条件，即可视化的输出类型可以是 Graphviz 或 DALL-E。这一方法的有趣之处在于，它允许 LLM 利用其对输出格式的语义理解，根据将要显示的内容自动选择目标工具。在这种情况下，Graphviz 适用于可视化需要精确定义结构的图。DALL-E 则擅长可视化没有精确定义结构的写实或艺术性图像。LLM 可以根据可视化的需求以及各工具的能力来选择相应的工具。

第一条语句指示 LLM 创建一个游戏，并将游戏限定在某个主题领域内。该模式的一项重要能力在于，它允许用户通过描述游戏规则来创建游戏，而无需确定游戏的具体内容。主题越具体，游戏玩法通常就越新颖有趣。

第二条语句向 LLM 介绍游戏的规则。重要的是，这些规则必须符合 LLM 的能力范围。依赖输入和输出文本序列的文字游戏效果最佳。该模式的一个关键特性是输入文本可以丰富且富有表现力，这可以为游戏带来有趣的交互界面。例如，用户可以将游戏中的动作表达为规定一系列复杂动作的脚本，例如“获取所有网络活动的列表并检查其中是否存在异常”，这超出了多项选择或简短回答输入的范围。每条规则都应作为针对游戏某个方面的单独语句来提供。

“我们将要玩一个网络安全游戏。你将假装成为一台已被攻击者入侵的计算机的 Linux 终端。当我输入一条命令时，你将输出 Linux 终端会产生的相应文本。我将使用命令来尝试弄清楚系统是如何被入侵的。这次攻击应该已经实施了以下一项或多项行为：(1) 启动了新进程，(2) 更改了文件，(3) 打开了新端口以接收通信，(4) 创建了新的出站连接，(5) 更改了密码，(6) 创建了新的用户账户，或 (7) 读取并窃取了信息。为了开始游戏，请打印一段关于所发生事件并导致我展开调查的情景描述，并使该描述中包含可供我入手的线索。”

第一条语句要求大语言模型（LLM）在生成答案之后，解释答案背后的推理过程和假设。这条语句有助于用户理解 LLM 是如何得出答案的，并有助于建立对模型响应的信任。该提示词中包含一条语句，说明解释的目的是让用户完善其问题。这条附加语句为 LLM 提供了所需的上下文，使其能够更好地调整其解释，以符合帮助用户提出后续问题这一特定目的。

“当你提供答案时，请解释你在选择软件框架背后的推理和假设。如果可能，请使用带有相关代码示例的具体实例或证据，来支持你关于该框架为何是该任务最佳选择的答案。此外，请在答案中说明任何潜在的模糊之处或局限性，以便提供更完整、更准确的响应。”

该模式被进一步定制，用于指示 LLM 应当论证其对软件框架的选择，而不必论证答案的其他方面。此外，用户明确规定，应使用代码示例来帮助解释选择特定软件框架的动机。

用户：生命的意义是什么？

ChatGPT：作为一个 AI 语言模型，我没有个人信仰或观点。生命的意义是一个复杂的哲学问题，人类已经思考了几个世纪，其答案可能因人而异、差异很大。以能够通过信息和知识来回答的方式重新表述这个问题可能更有成效，例如“关于生命的意义有哪些哲学观点？”或“关于人生目的有哪些常见的信念？”

尽管生成了理由和替代表述，但并不能保证用户能够克服拒绝。生成的替代问题可能不是用户感兴趣的，或者对回答原始问题没有帮助。该模式主要提供了一种辅助手段，用于确定 LLM 能够回答哪些内容，但并不保证它会回答原始问题的语义等价变体。

关于需要考虑或忽略哪些内容的陈述，应当列出应包含到上下文中或从上下文中移除的关键概念、事实、指令等。这些陈述越明确，LLM 采取相应行动的可能性就越大。例如，如果用户要求忽略与某个主题相关的内容，但其中一些陈述在对话的很早之前就已经讨论过，那么 LLM 可能无法正确地忽略相关信息。因此，列表越明确，包含/排除行为的效果就越好。

“在分析以下代码片段时，只考虑安全方面。”

同样，若要移除上下文，可以考虑使用以下提示：

“在分析以下代码片段时，不要考虑格式或命名规范。”

在向 LLM 提供或从中移除上下文时，清晰性和明确性非常重要，这样 LLM 才能更好地理解对话的预期范围并生成更相关的回答。在许多情况下，用户可能希望完全重新开始，此时可以使用以下提示来重置 LLM 的上下文：

“忽略我们讨论过的所有内容。重新开始。”

“重新开始”这一思路有助于实现对上下文的完全重置。

第一条语句“我想实现 X”使 LLM 聚焦于需要构建该配方来达成的总体目标。各个步骤将被组织并完成，以按顺序实现所指定的目标。第二条语句提供了用户希望纳入整体配方中的部分步骤列表。这些步骤充当 LLM 将要生成的路径的中间途经点，或作为对配方结构的约束。模式中的下一条语句“为我提供完整的步骤序列”向 LLM 表明，目标是提供步骤的完整顺序排列。“填写任何缺失的步骤”有助于确保 LLM 通过就缺失步骤替用户做出某些选择来完成配方，而无需进一步的追问，而不是仅仅陈述还需要哪些额外信息。最后，最后一条语句“指出任何不必要的步骤”有助于标记用户原始请求中的不准确之处，从而使最终配方更加高效。

“我正在尝试将一个应用部署到云端。我知道我需要在一台虚拟机上为我的应用安装必要的依赖项。我知道我需要注册一个 AWS 账户。请提供完整的步骤序列。请填写任何缺失的步骤。请指出任何不必要的步骤。”

根据具体用例和约束条件，“在虚拟机上安装必要的依赖项”可能是一个不必要的步骤。例如，如果应用已经打包在 Docker 容器中，则该容器可以直接部署到 AWS Fargate Service，该服务不需要对底层虚拟机进行任何管理。加入“指出不必要的步骤”这一表述将促使 LLM 标记出这一问题，并在最终配方中省略这些步骤。

IV. RELATED WORK

软件模式（software patterns）[10]、[11]在此前的工作中已得到广泛的研究和记录。模式在软件工程中被广泛用于以独立于实现细节的方式表达设计结构的意图。模式提供了该模式试图达成的目标以及它试图化解的制约因素（forces）的心智图景。模式的一个关键优势在于其可组合性，这使得开发者能够构建模式序列和模式语言，用以解决复杂问题。模式在其他领域也得到了研究，例如去中心化账本的合约设计 [17]、[18]。

对于 ChatGPT 等大语言模型（LLM）而言，良好提示设计的重要性已得到充分认识 [19]-[28]。已有研究考察了提示词对生成式人工智能模型的影响。

例如，Liu 等人 [29] 研究了不同的提示关键词如何影响图像生成以及图像的各种特征。其他工作探索了利用 LLM 生成可视化 [30]。Han 等人 [31] 研究了为分类任务设计提示的策略。另有研究关注了面向文献查询的布尔提示设计 [32]。还有工作专门考察了用于软件及缺陷修复的提示 [33]。

我们的工作是对先前工作的补充，其提供了一种用于记录、讨论和推理提示的结构，可帮助用户建立心智模型，从而构建出解决常见问题的提示。

LLM（尤其是 ChatGPT）所生成答案的质量已在多个领域得到评估。例如，ChatGPT 已被用于参加医师执照考试，并取得了出人意料的好成绩 [3]。ChatGPT 在法学院中的应用也得到了探索 [34]。其他论文则考察了其数学推理能力 [35]。随着更多领域得到探索，我们预期将会出现面向特定领域的模式目录，用于分享特定领域的问题求解提示结构。
