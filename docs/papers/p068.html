Closing the safety Verification Loop, FMEDA Driven Fault Simulation and Advanced Debug for Efficient Fault Classification

闭环安全验证：FMEDA 驱动的 Fault Simulation 与面向高效故障分类的 Advanced Debug

简介

论文针对 ISO 26262 功能安全验证中 FMEDA 与 fault simulation 长期割裂、故障列表通用未过滤、缺乏可追溯性导致多轮迭代与收敛困难的问题，提出由 FMEDA 输出直接驱动 fault simulation 的闭环方法。方法在 ISO 26262 part 11 定义的 elementary subpart 粒度解析 FMEDA 数据，借助 Synopsys VC FSM 自动生成 safety verification plan，将 failure mode 映射到 RTL/gate-level 可仿真故障模型，再以 STL workload 模拟在役诊断行为、按安全机制设置 strobe 点，迭代执行 FSIM 直至达到 FMEDA 定义的目标 DC，并对未分类故障引入 AI 辅助 debug（论文注明该阶段仍在进行中）。在配备多个安全机制的量产 automotive SoC block 上验证：故障规模减少超 33%，人工 debug 工作量减少近 66%，算力资源节省 3-5×，SPFM/LFM 覆盖率与传统方法持平或更优，且每个 FSIM 检测结果与 FMEDA 条目一一映射形成可审计闭环。该方法与本团队 2.5/2.6 域的 FuSa TFMEA/FMEDA 与 fault simulation 关联论证工作高度契合。

问题

ISO 26262 要求证明 parity/ECC、watchdog、lockstep、reset monitor 等安全机制能检测或控制相关硬件故障，并以 SPFM/LFM 量化、ASIL-D 要求未检测单点故障低于极小阈值。但工业界现有流程中 FMEDA（定义需保护的对象与安全机制）与 fault simulation（度量 DC 覆盖）相互独立执行，导致重复工作、假设不一致、可追溯性缺口：FMEDA 识别的故障未直接映射到仿真 campaign，缺乏安全上下文引发多轮迭代、难以跟踪，安全验证收敛困难。

方法

建立 FMEDA 输出到 fault simulation 环境的直接数据驱动链路：(1) 在 elementary subpart 级解析 FMEDA 数据，提取 failure mode、受影响模块、DC 目标与安全目标，使每次故障注入可回溯至 FMEDA 原始条目；(2) 用 Synopsys VC FSM 自动生成 safety verification plan，将每个 FMEDA failure mode 映射到 RTL/gate-level 的一个或多个可仿真故障模型与区域；(3) gate-level 故障注入，campaign 按安全相关性优先排序，ASIL 关键单元先验证；(4) 用 Software Test Libraries (STLs) 模拟在役诊断行为作为 workload，基于 FMEDA 安全机制选取 strobe 观测点；(5) 迭代 FSIM：分析 undetected faults（blocked propagation、missing strobe、stimuli 不足）并精化 workload 与观测逻辑；(6) 对仍未分类的故障用 AI/ML 做结构分析、故障行为模式识别与根因预测（进行中）；(7) DC 达标后正式分析、证明并关闭 block。

关键结果

相比传统穷举故障注入方法，故障规模（fault population）减少超过 33%

人工 debug 工作量减少近 66%

计算资源占用降低 3-5×

在配备多个安全机制的量产 automotive SoC block 上完成验证，证明可扩展性与工业适用性

SPFM/LFM 诊断覆盖率达到与传统方法相同或更好水平

每个 FSIM 检测结果映射到对应 FMEDA 条目，形成一对一可追溯闭环，消除冗余故障 campaign

创新点

主要区别在于打破传统流程中 FMEDA 与 fault simulation 各自独立、故障列表通用且未过滤的模式：以 elementary subpart 粒度从 FMEDA 数据精确界定需仿真的故障、相关检测机制与安全覆盖指标，通过 VC FSM 自动生成验证计划，实现 FMEDA 条目与仿真证据的一对一映射和审计就绪；同时将故障分类 debug 升级为 AI 辅助的结构分析与根因预测，并把 fault simulation 从统计性工作转变为可重复、可追溯、符合标准的验证方法学。

1. Abstract

向自主出行的快速迈进正在重塑汽车行业格局，并加速半导体技术的演进。随着制造商追求更高的集成密度和更低的工作电压，现代半导体越来越容易受到随机硬件失效的影响，这类失效可能在器件生命周期内不可预测地发生。高级驾驶辅助系统（ADAS）和自动驾驶车辆（AV）功能依赖这些数字与模拟系统来执行关键的实时应用，这对其验证与安全性提出了至关重要的问题。

ISO 26262 和 IEC 61508 等功能安全标准要求对硬件安全机制进行全面分析，这通常通过失效模式、影响与诊断分析（FMEDA）来实施。然而，传统的验证和故障仿真流程往往独立于 FMEDA 活动运行，从而导致脱节。未结合 FMEDA 识别出的故障可能无法直接映射到仿真活动中，而缺乏这种安全上下文会导致多轮迭代、缺乏跟踪，并给实现稳健的安全验证收敛带来挑战。

本文提出一种方法学，将 FMEDA 输出与故障仿真执行直接衔接，从而实现一种验证驱动的方法，使仿真活动能够精确地根据 FMEDA 结果进行定制。通过利用 FMEDA 数据，该方法精确定义了必须仿真哪些故障、指定相关的检测机制，并建立与安全相关的覆盖率指标。

本工作的另一项贡献是一种先进的调试方法学，用于解决故障分类中的歧义问题——这在大规模故障仿真活动中正日益成为一项关键需求。本文详细阐述了：

本工作将使验证工程师、功能安全经理和电子设计自动化（EDA）工具开发人员受益，既提供方法学上的进步，也提供可适用于汽车、航空航天和工业领域安全关键设计的实用见解。

2. Introduction and Problem Statement

功能安全标准（如 ISO 26262）要求硬件设计证明其安全机制能够可靠地检测或控制可能导致危险行为的故障。随着片上系统（SoC）复杂度的不断提升，要在不投入过多人工工作或仿真成本的前提下证明安全覆盖率目标已经达成，变得极具挑战性 [1][5]。

在实践中，安全验证依赖于两项活动：

FMEDA 定义了需要保护的对象及其安全机制，而故障仿真则衡量安全机制所实现的诊断覆盖率（DC）。尽管这两项活动都指向相同的安全目标，但它们通常被独立执行，从而导致重复劳动、假设不一致以及可追溯性方面的缺口。这促使人们需要一种将 FMEDA 意图直接与仿真证据相关联的统一方法 [4]。

FMEDA 用于识别哪些元件需要安全机制，以及能够达到何种诊断覆盖率（DC）。故障仿真通过注入故障并检查安全机制是否正确响应，从而提供实验证据。

3. Proposed Methodology

本文所提出的方法在 FMEDA 输出与故障仿真环境之间建立了直接的、数据驱动的关联，有效地闭合了验证闭环，确保故障分析可追溯、高效且聚焦于安全。与 FMEDA 和故障仿真各自独立运行的传统流程不同，这种集成方法使仿真活动直接对准与安全相关的设计元素，从而减少冗余并提升覆盖率置信度。

A. FMEDA Data Extraction (Elementary Subpart Level)

流程的第一步是在基本子部件（elementary subpart）层级解析 FMEDA 数据，提取诸如失效模式、受影响模块、诊断覆盖率（DC）目标以及相关安全目标等信息。这种结构化提取确保仿真期间注入的每一个故障都有明确的依据，并可追溯至原始 FMEDA，从而强化合规文档与审计就绪能力。通过在基本子部件层级开展工作，该流程还允许对安全验证进行细粒度控制，避免对非安全关键信号进行不必要的仿真 [5][6]。基本子部件的定义如 ISO 26262 第 11 部分所定义，如图 2 所示。起源于扇入至基本子部件（时序元件）的门电路中的固定型故障（stuck at fault），最终该错误具有导致失效的潜在可能。

C. Fault Simulation Execution

精确理解安全相关故障及其在设计中的映射，对于开展高效的故障仿真活动至关重要。如果故障集合定义不清晰，仿真运行可能变得不完整或规模不必要地庞大。为避免这种情况，执行流程首先提取细粒度的 FMEDA 数据，并生成具有针对性且经过优先级排序的故障仿真计划。这确保了仿真资源得到高效利用、诊断响应得到正确解读，并且所得的覆盖率指标准确反映 ISO 26262 安全目标。[2]

故障仿真阶段利用多种优化与自动化技术，以最大化效率和诊断覆盖率（DC）。所选故障在门级注入，并基于安全机制对诊断响应进行监测。仿真活动按安全相关性排定优先级，确保 ASIL 关键元素得到优先验证。

· Workload Definition :

在故障提取之后，需定义适当的测试激励，以激活与每个 FMEDA 分区相关联的安全机制。软件测试库（Software Test Libraries, STLs）用于模拟真实的现场诊断行为并触发故障响应。

· Strobe Point Selection :

基于 FMEDA 安全机制，在 FSIM 环境中添加关键观测点（strobes，选通点）。选通点确保故障效应被正确捕获，并与预期的诊断响应相关联。[2][5]

· Fault Simulation and Analysis :

使用所选的软件测试库（STL）进行故障仿真，以验证 FMEDA 范围内的诊断覆盖率（DC）。仿真完成后，对任何未检测到的故障进行分析，以识别诸如传播路径被阻断、选通点缺失或测试激励不足等潜在问题。利用这些反馈，对工作负载和观测逻辑进行迭代改进，以提高诊断覆盖率并消除验证缺口。[2]

· Advanced Fault Debug and Classification :

对于仍未被分类或存在歧义的故障，采用人工智能（AI）进行更深层次的结构分析，识别故障行为模式并预测根本原因。机器学习模型通过将故障动态地分类为明确的类别，并建议有针对性的故障注入以提升覆盖率，从而帮助解决检测中的不确定性；该阶段目前正在进行中。

· Final Validation:

一旦达到 DC 目标，即对结果进行分析并进行形式化证明，随后关闭该模块。

5. FSIM Results and Conclusion

基于 FMEDA 驱动的故障仿真方法为汽车 SoC 的安全验证引入了一种结构化且符合 ISO 26262 的途径。FSIM 的每个检测结果都会映射到其对应的 FMEDA 条目，从而在仿真故障行为与其关联的安全目标或诊断机制之间建立一一对应的关系。该过程建立了一个闭环系统，确保可追溯性、准确性和审计就绪性。这种对齐消除了冗余的故障仿真活动，并提升了 SPFM 和 LFM 等关键安全指标。[3]
