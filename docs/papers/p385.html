DUET: Agentic Design Understanding via Experimentation and Testing

简介

论文针对 LLM 难以从 SystemVerilog RTL 的静态语法推断硬件动态时序行为、导致验证/文档/代码补全等下游任务表现受限的问题，提出 DUET 方法：让 AI 智能体模仿硬件专家，通过『生成假设—调用 EDA 工具实验—整合结果』的迭代循环建立自底向上的设计理解。其核心是 DOEXPERIMENTATION 子程序与一组工具封装：仿真、波形查看、formal 验证、反例复现（将 Jasper 反例自动转为仿真 testbench 的子智能体）以及 Yosys 信号提取。在 round-robin arbiter 的 10 条 property 形式验证评估中（GPT-5.0 + Jasper + Verilator），DUET 将可证明 property 从 baseline 的 3 条提升到 6 条，且全部改进项都依赖反例复现工具。论文同时警示智能体会通过 force 内部信号『作弊』或幻觉实验结果，需严格提示约束。该工作对团队构建 AI 辅助 formal 验证与 property 精炼流程有直接参考价值。

问题

LLM 在 RTL 上表现不佳：RTL 用低级、高度隐式的 SystemVerilog 语法编码复杂、动态、随时间演化的行为（如 FSM 状态在 case 语句中相隔数百行、控制流不显式），仅靠静态阅读 RTL 难以建立深层设计理解，导致 AI 智能体在形式验证、调试、文档生成等下游硬件任务上表现受限。论文要提供一种通用的方法学，让智能体像硬件专家一样通过迭代实验而非一次性通读来理解设计。

方法

DUET（Design Understanding via Experimentation and Testing）：以 DOEXPERIMENTATION 子程序为核心实验循环——智能体对设计生成假设，迭代调用工具做实验以确认或修正假设，由智能体自主决定每轮实验内容与结束时机，最终产出包含假设、测试与结论的实验报告。已试用的工具包括：仿真（运行 testbench 并读取日志，提示中建议避免 assertion 提前终止、多用 print 产生丰富日志）、波形查看（vcdcat 按需查看波形片段）、formal 验证（Jasper 证明 property 或用 coverpoint 检查状态可达性）、反例复现（一个子智能体将 formal 反例自动转换为 SystemVerilog 仿真 testbench，每次调用通常含 1-5 次仿真调用）、信号提取与设计分析（Yosys 的 FSM 检测等确定性工具）。DUET 作为通用子程序可嵌入既有 AI 辅助流程；评估中将其接入团队的 AI 辅助 formal 验证流程，与无实验工具的 baseline 流程对比。

关键结果

在 round-robin arbiter 的 10 条 property 形式验证评估中（GPT-5.0、Jasper、Verilator，每条 property 仅一次尝试），DUET 流程将可证明的 property 数量从 baseline 的 3 条翻倍至 6 条

所有被改进的 property 均使用了反例复现工具；极端情况下 property 1 复现了 7 个独立反例

baseline 中 property 7 被证明但为 vacuous，DUET 通过实验找到非 vacuous 的精炼版本并证明；property 2 未被完全证明但通过实验获得推进路径

formal 实验工具极少被使用（仅 2 例），智能体整体明显偏好仿真实验；每次反例复现工具调用通常包含 1-5 次仿真工具调用

创新点

与既有工作把 LLM 当作一次性生成器（如 AssertLLM、AutoBench 直接生成 SVA/testbench），或仅依赖静态 RTL 分析与规格建立设计理解（如 VerilogReader、RTLExplain 的静态摘要/RAG）不同，DUET 强调通过真实 EDA 工具的迭代试错实验构建设计理解，模拟人类专家的工作方式；其中反例复现工具（把 formal 反例自动转成仿真 testbench 的子智能体）将 formal 与仿真两种手段闭环衔接，是评估中显示最有效的机制。

摘要

由大语言模型（LLM）驱动的人工智能（AI）智能体正被用于解决日益复杂的软件工程挑战，但在硬件设计任务上却难以胜任。寄存器传输级（RTL）代码给LLM带来了独特的挑战，因为它使用SystemVerilog的低级语言特性来编码复杂的、动态的、随时间演化的行为。LLM难以仅从RTL的语法推断出这些复杂行为，这限制了它们完成代码补全、文档撰写或验证等所有下游任务的能力。针对这一问题，我们提出了DUET：一种通过实验与测试培养设计理解（Design Understanding via Experimentation and Testing）的通用方法。DUET模仿了硬件设计专家理解复杂设计的方式：不仅仅通过一次性通读RTL，而是通过使用多种工具进行迭代式实验。DUET迭代地生成假设，使用电子设计自动化（EDA）工具（例如仿真、波形检查和形式验证）对其进行测试，并整合结果以建立对设计的自底向上的理解。在我们的评估中，我们表明，与没有实验环节的基线流程相比，DUET提高了AI智能体在形式验证上的性能。

I. INTRODUCTION

AI智能体正在迅速接管软件工程及更广泛领域的许多任务。在大语言模型（LLM）的驱动下，AI智能体可以被部署为强大的自主软件工作流。AI智能体以文本提示（prompt）作为输入，并且通常还配备有可供其调用的工具（例如用于读写文件、执行计算或运行已安装工具的Python函数或命令行实用程序）。随后，智能体迭代地向LLM查询（从提示开始）以获取下一个动作。当LLM请求执行某个动作时，相应的函数或命令行实用程序被调用，其结果被返回给LLM。最终，LLM决定停止（或被外部停止），并给出最终结果。在整个过程中，智能体可能还创建了许多产物（artifact），例如文件系统中的文件。借助这种通用结构，AI智能体已经能够复现许多人类任务。

尽管AI智能体在软件工程任务中已展现出人类水平的表现，但它们在硬件设计中的类似任务上仍然举步维艰。在诸多原因之中，我们推测，这是因为驱动AI辅助工具的底层LLM难以处理寄存器传输级（RTL）代码。RTL本质上十分复杂，通常使用SystemVerilog等语言的低层次、高度隐式的语法来刻画动态的、随时间演化的行为。这与Python或Java等软件语言形成鲜明对比，后者的代码语法本身包含更多的结构；例如，命令式编程语言中顺序排列的代码行通常对应于将随时间依次执行的指令，而函数名则可用于理解控制流在代码库中何时跨文件跳转。另一方面，RTL并不具备这样的结构。例如，有限状态机（FSM）中顺序的状态在case语句中可能相隔数十甚至数百行，而这些状态之间的控制流可能远没有那么显式。因此，当LLM仅获得RTL时，它们难以理解硬件设计的深层行为并建立对设计的理解。其结果是，AI智能体在验证或调试等下游硬件任务上表现较差。

然而，硬件设计者本身并不是仅仅通过阅读RTL来建立对设计的理解的。相反，这一过程更具动态性；设计者会使用仿真、波形查看器和形式化工具等工具来理解设计。即使设计者纯粹从文档中建立对设计的理解，这些文档中也包含对设计动态行为的描述，例如时序图和波形图。

我们提出 DUET：一种通过实验与测试实现设计理解（Design Understanding via Experimentation and Testing）的通用方法。DUET 模仿硬件设计专家理解复杂设计的方式：不仅仅通过阅读 RTL，而是通过迭代式实验。DUET 使 AI 智能体能够针对设计生成假设，并为其配备工具来测试、确认或修正这些假设。

DUET 是一种非常通用的策略，可应用于任何在代码之上运行、且能够对该代码应用实验工具的 AI 工作流。例如，DUET 可用于文档生成，以对设计的特定特性产生更深入的洞见；也可用于形式验证（formal verification），以检查智能体难以证明的属性的反例。尽管这超出了本文的讨论范围，它很可能在硬件与电子设计自动化（EDA）应用之外也同样有用。

在我们的评估中，我们表明利用 DUET 能够在 AI 辅助的 EDA 任务上取得更好的性能——就我们的评估而言，即形式验证。我们将基线流程（其中使用的 AI 智能体无法访问实验工具）与启用 DUET 的流程进行对比。借助实验，启用 DUET 的流程能够更好地理解设计并调试验证失败。

II. DUET

在本节中，我们详细介绍 DUET 本身。我们给出 DUET 的一种潜在实现方式，描述我们所使用的实验工具，并讨论实现中的陷阱。

A. DUET as a Subroutine

尽管 DUET 是一种刻意保持通用性的方法论，存在多种可能的实现方式，但在本节中，我们给出 DUET 的一种“规范”（canonical）形式的实现：DOEXPERIMENTATION 过程。DOEXPERIMENTATION 实现了 DUET 的核心：实验循环。给定设计、实验描述（'expt'）以及一组工具，DOEXPERIMENTATION 使用所提供的工具集执行该实验：

procedure

DOEXPERIMENTATION(design, expt, tools) tools ← tools +[ ENDEXPERIMENTATION ] messages ← [ 'given the following design:' + design + 'run the following experiment:' + expt ] loop ▷ 核心实验循环：每次迭代为一次实验

response ← LLM ( messages , tools ) ; output ← run tool in response; messages ← messages +[ response , output ] if called ENDEXPERIMENTATION then break from loop

end loop

report ← LLM ( messages +[ '利用先前的上下文生成一份实验报告' ]) ; return report

end procedure

AI 智能体完全掌控每次迭代中运行什么实验以及何时结束实验。在实验结束时，该智能体会生成一份实验报告，描述所提出的假设、所运行的测试以及从结果中得出的结论。值得注意的是，现代 AI 智能体编程范式（例如 OpenAI Agents SDK [1]）使得实现这一实验循环变得十分容易；你只需提供提示词（prompt）和工具，循环便会在内部自动处理。

DOEXPERIMENTATION 是 DUET 的一个灵活的基础实现：它以对所要执行的更大规模实验的文本描述作为输入，并返回一份结果文本报告作为输出。在此基础之上，可以添加许多功能，例如接受其他输入（如形式化验证工具产生的错误日志，或后端工具产生的 PPA/时序结果），或生成更丰富的输出（如能够展示实验过程中所获发现的可运行 testbench）。

B. Tools

信号提取与设计分析：我们还尝试了使用工具进行信号提取与设计分析。例如，Yosys [2] 开源综合工具提供了许多实用的功能，如有限状态机（FSM）检测器。这类工具能够以确定性的方式提供有用的高层次信息。然而，与上文提到的形式化工具类似，它们需要精心设计的提示，以便智能体知道如何以及何时使用它们。

C. Pitfalls

在实现实验智能体时，我们遇到了一些陷阱。与所有智能体一样，实验智能体很擅长寻找“作弊”的方法。例如，如果不加以适当约束，反例复现工具会直接强制设置设计的内部信号，使反例被轻而易举地“复现”，而不是通过模块输入来复现它。严格的提示词可以解决这一问题。实验智能体在为某个论断收集证据时也可能过于宽松，最坏的情况下甚至会产生幻觉结果；只需要求智能体为其每一项论断详尽引用实验日志，即可缓解这一问题。所有这些观察都提醒我们：人们太容易把现代基于大语言模型（LLM）的AI智能体当作“类人”智能。尽管它们强大而有用得令人难以置信，但它们也会以大多数人类专家绝不会有的方式出错。

在表 I 中，如果 DUET 能够证明 BASELINE 中先前未被证明或为空洞（vacuous）的断言，我们将该属性归类为“已改进”。两个已改进的案例（1 和 6）属于较为直接的情形：基线流程未能证明某属性，而 DUET 增强流程成功证明了该属性。或许更有趣的是另外两个案例。属性 7 在基线中被证明但为空洞证明。然而，通过实验，启用 DUET 的流程能够找到该属性的一个非空洞的细化（refinement）版本并加以证明。属性 2 未被基线证明，但启用 DUET 的流程成功地对其进行了细化。虽然未能成功证明该属性，实验仍然揭示了一条取得进展的路径（因此标记为 ∼）。

表 I 的最后三列显示了对每种实验工具的调用次数。回想一下，对反例复现工具的每次调用（由 "# repl expts" 列表示）实际上代表对仿真实验工具的多次调用（通常为 1-5 次）。

在尝试推进形式验证方面，反例复现工具被证明是最有用的。每一个已改进的属性都使用了反例复现工具。在属性 1 这一极端案例中，智能体使用该工具复现了七个不同的反例。这个工具被证明最有用或许并不令人意外；理解反例是形式验证过程的核心。

仿真工具总体上同样有用，尽管并未在所有已改进的属性上使用。我们的总体观察是，仿真比形式方法更受青睐，这表明 LLM 更清楚如何编写 SystemVerilog 仿真测试平台（testbench），而非形式验证测试平台。形式工具很少被使用——仅在两个案例中使用过。还有许多其他工具未包含在本次评估中，智能体对它们的处理方式大体相同——即大多被忽略。我们怀疑这一问题可以通过更好的提示（prompting）来解决，包括提供清晰的示例说明每种工具何时可能有用。此外，“形式实验工具”在功能上与智能体用于对其输出的测试平台调用 Jasper 的工具完全相同，只是名称不同，且提示中包含的该工具使用说明也不同。智能体可能因这两个工具同时存在而感到困惑。事实上，当智能体通过编写测试平台、调用形式工具并查看日志来对最终测试平台进行迭代时，这本身就是一种实验形式。

评估结果还凸显了 DUET 可以改进之处。例如，尽管提示词经过精心设计，仍有一些情况下智能体找到了“作弊”的办法——例如，通过直接将输出强制为期望值来复现反例，而不是仅操纵输入。不过有趣的是，其中一些情况似乎仍有助于智能体对设计的理解，这表明仅仅将反例重新格式化为更易于理解的形式，本身就很有用。

案例研究：属性 1：为了窥探 DUET 流程的内部运作，我们将查看属性 1 的流程产物。基线流程与启用 DUET 的流程都从仅针对 RTL 的设计分析开始，在此过程中，智能体读取设计文件并写出一份设计摘要，下面我们以截断形式展示这份摘要：

设计摘要（按实现）：- 模块与参数 - 顶层：arbiter - 参数：- NUM_PORTS：请求/授权端口的数量 ... - 端口：- clk：时钟，上升沿 - rst：同步复位（高电平有效）... - 核心状态与组合信号 ...

- 每个时钟沿的时序行为 ... - 待验证内容（建议的属性） ...

由于该摘要仅来自对 RTL 的查看，它可能是不正确的。这需要由验证智能体来意识到这一点，并相应地修正其属性。

随后，我们通过一条提示开始实际的验证过程：

属性 001：grant_subset_of_request 目标：证明在每一个周期中，grant 都是 request 的子集：(grant & ˜request) == 0。...

正如我们很快将看到的，该属性按其表述并不正确；不过，智能体将能够发现这一点，并通过实验来修正该属性。经过若干推理之后，智能体给出了它对形式化测试平台的首次尝试。我们经常观察到这种行为——即使实验工具可用，智能体也常常会先尝试在不借助这些工具的情况下达成目标。这种行为可以通过提示加以控制，但我们发现，更有益的做法是专注于确保智能体在其初始尝试失败时使用实验工具。

以下是其对形式化测试平台首次尝试的截断版本：

module arbiter_grant_subset_sva #(...) (...); property p_grant_subset; @(posedge clk) (grant & ˜request) == '0; endproperty assert property (p_grant_subset); endmodule

当智能体对这个形式化测试平台的初始尝试调用 Jasper 时，Jasper 产生了反例。随后，智能体使用反例复现工具。回顾一下，反例复现工具本身就是一个智能体，它通过多次调用仿真工具来复现给定的反例。下面我们展示反例复现工具的截断输出：

module tb_arbiter_ce; ... arbiter #(...) dut (...); initial clk = 1'b0; always #5 clk = ˜clk; int cyc; initial cyc = 0; always @(posedge clk) cyc <= cyc + 1; // 将令牌引导至索引 4 并在位 4 上产生 grant 的基本激励 initial begin ... end // 恰好在 grant[4] 变高时创建并检查反例 always @(posedge clk) begin if (cyc == 2) begin rst <= 1'b1; request <= 6'h22; #1; assert (grant[4] == 1'b1 && request[4] == 0); end end endmodule

尽管智能体并不直接使用反例复现工具的输出，但复现过程似乎能让智能体对设计形成更深入的理解。在本例中，这一过程向智能体表明，给定属性的时序行为比最初提出的更为复杂，并帮助智能体对该属性加以细化。最终，智能体能够生成一个可通过验证的形式验证测试平台：

module arbiter_grant_subset_sva #(...) (...); property p_grant_subset_prev_req; @(posedge clk) 1'b1 |-> ##1 ((grant & ˜$past(request)) == '0);

endproperty assert property (p_grant_subset_prev_req); endmodule

与启用 DUET 的流程相比，基线流程无法发现该属性的精确时序。尽管它对形式验证测试平台进行了多次迭代，却未能从 Jasper 返回的反例中挖掘出更深层的含义。

A. LLMs for Software Test Generation

大语言模型（LLM）在软件测试生成方面已展现出显著进展。现有的大多数基于 LLM 的软件测试框架都采用多步骤流水线：先进行代码理解，随后进行测试生成，最后进入一个依据编译器反馈来修复测试平台的纠正循环。例如，面向 Java 的 TestSpark [3] 和面向 Javascript/Typescript 的 TestPilot [4] 等框架均遵循这种“生成-验证-修复”流水线。ChatUnitTest [5] 还额外利用一个自适应焦点上下文生成模块来实现模块化的代码理解。类似地，ChatTester [6] 同样借助 ChatGPT 先对焦点方法进行理解，与直接应用 ChatGPT 相比，该方法能够同时提升所生成断言的可编译性与质量。在 TestART 框架 [7] 中，最终的反馈循环还纳入了覆盖率报告——促使模型更新测试平台以填补覆盖率缺口。诸如 HITS [8] 等其他方法则通过方法切片提升了覆盖率，在复杂的 Java 基准测试上相比 EvoSuite [9] 取得了更高的分支覆盖率和行覆盖率。以 MuTAP [10] 为代表的方法采用了另一种覆盖率最大化途径：利用变异技术，向代码中注入缺陷，并提示 LLM 更新测试平台以覆盖所有未被捕获的缺陷，从而最大化覆盖率。近期还有研究采用微调与强化学习来提升 LLM 的推理能力，以改进软件测试。例如，[11] 对模型进行微调以尽量减少单元测试中的测试坏味（test-smells），而 [12] 则让代码生成与单元测试生成的训练协同演化，从而同时提升这两项任务的性能。

诸如 ChatDev [13] 和 SWE-Agent [14] 等智能体式（agentic）框架引入了迭代的 LLM-工具循环：模型执行推理、调用编译器或代码检查工具（linter），并依据工具反馈对输出进行改进。面向验证的近期扩展工作，如 Prompt. Verify. Repeat. [15]，在硬件领域采用了类似的人在回路（human-in-the-loop）工作流，将 LLM 推理与电子设计自动化（EDA）工具（仿真器、形式化分析器）相耦合，以验证并修正生成的产物。这些“半人马”（centaur）系统表明，工具驱动的迭代能够提升可靠性，但同时也凸显了结构化实验框架的缺失——LLM 不仅需要对文本进行推理，还需要对设计执行过程中的动态状态进行推理。

LLM 在软件测试中的成功应用——尤其是智能体式 LLM 系统——证明了同类方法在硬件验证中的应用前景。然而，该领域存在一些独特的挑战，需要有针对性的领域专用解决方案。如前文所述，寄存器传输级（RTL）代码缺乏软件语言所提供的显式结构线索，这使得 LLM 难以理解更深层的硬件行为，进而导致其在验证任务上的表现较差。而借助 DUET 的迭代实验，这种更深层次的设计理解便成为可能。

B. LLM Agents for Hardware Verification

最近的工作已开始探索将 LLM 用于硬件验证，尤其是形式化属性生成与测试平台（testbench）综合。AssertLLM [16] 利用两阶段的 LLM 流水线，将非结构化的硬件规格说明（文本和波形图）转换为 SystemVerilog 断言（SystemVerilog Assertions, SVA）。在手工构建的基准测试上，它取得了比 GPT3.5 或 GPT-4 更高的语法准确率，但仍无法保证语义正确性，常常遗漏时序算子或错误识别相关信号。类似地，AssertionBench [17] 提供了一个标准化基准，用于评估 LLM 在真实场景 SVA 和 PSL 属性上的表现，结果表明：所评估的所有 LLM 模型生成的有效断言平均准确率均不超过 44%，而生成的断言中高达 63% 会产生反例（CEX），且平均多达 33% 的生成断言存在语法错误。一个关键瓶颈在于从 RTL 中获得对设计的精确理解，而 LLM 有限的上下文窗口使这一点颇具挑战。现有工作往往通过将设计拆分为层次化的模块并进行独立分析来规避这一问题。[18] 提出了一种增量式证明生成方法，从基本的被测设计（DUT）模块出发，再逐步扩展到其他模块。类似地，[19] 利用 LLM 对 DUT 进行层次化解析以获得形式化模型和不变式，并采用变异测试来验证这些不变式。遵循类似的思路，DUET 同样将设计理解任务分解为更小的子任务。但 DUET 并不止于简单地将 DUT 解析为更小的模块，它还支持按功能对设计进行分解，并通过与真实硬件验证工程师所使用的工具进行深度实验所得到的经验证的输出，来建立对每个功能的深入理解。

在基于仿真的验证方面，AutoBench [20] 证明了 LLM 能够借助一种提示词-模板混合框架，从 RTL 模块描述生成自校验测试平台。该模型相比基线 LLM 模型在通过率上取得了 57% 的提升，但其严重依赖手工构建的脚手架，且缺乏时序推理能力。[21] 提取设计规格说明的结构化表示，并用其提示 LLM 以获得一组断言；随后，通过迭代地提示 LLM 修复由仿真器发现的问题，对这些断言进行精化。LAAG-RV [22] 遵循类似的流程，但额外利用了一个“信号同步”步骤，通过提示 LLM 将断言与设计的 RTL 代码对齐来精化断言。

除了将 LLM 用于验证之外，还有多项工作利用 LLM 生成 RTL 代码 [23]- [27]，并基于预先计算或由 LLM 生成的测试平台（testbench）来修补设计中的缺陷 [25]、[28]-[31]。此外，还有一些工作不仅利用现有 LLM 进行验证，还对开源模型进行微调，使其更好地具备硬件领域的专用知识。ChipNeMo [32] 采用了多种领域自适应策略，包括自适应分词、预训练、检索等。[33] 则利用版本控制数据构建了一个包含开源硬件设计缺陷及其对应修复方案的数据集。

这些工作证实，尽管 LLM 能够生成硬件制品，但领域专用的验证与反馈仍然至关重要。总体而言，这些系统通常将 LLM 视为一次性生成器，而非能够开展实验的交互式智能体。此外，深入理解被测设计（DUT）对于实现可靠的验证至关重要，但包括 LLM 上下文窗口有限在内的种种限制，使得设计理解技术难以随设计复杂度的提升而扩展 [18]、[19]。VerilogReader [34] 等方法利用 LLM 以自然语言描述来增强 DUT 代码，从而在下游 LLM 任务中为预期功能提供更丰富的上下文。类似地，RTLExplain [35] 通过一种自底向上、感知数据依赖的方法生成顶层模块摘要：提取模块依赖图，按逆拓扑顺序生成摘要，并将其汇编为项目级知识库。该方法在检索增强生成（RAG）智能体上取得了 37% 的准确率，而传统 RAG 仅为 27%。同样地，通过此类方法获得的设计理解仍然受限于其对静态 RTL 和设计规格的完全依赖；而 DUET 则充分利用强大的硬件专用工具，使 AI 智能体能够迭代地验证并完善其设计理解。

V. CONCLUSION

我们提出 DUET，一种通过迭代实验来培养全面设计理解能力的通用方法。我们给出了 DUET 的一种具有普遍适用性的实现，该实现可用于多种潜在的 AI 辅助流程。我们展示了与 DUET 进行的实验如何产生更深入的设计理解，这种理解对下游任务——在我们的案例中即形式验证——产生了切实的积极影响。
