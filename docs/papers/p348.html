Enhanced Verbosity Methodology

增强型消息详细度控制方法学（Enhanced Verbosity Methodology, EVM）

简介

大型垂直集成 UVM testbench 在子系统/系统级会集成数十至数百个 predictor、checker 与 agent，日志噪声与消息构造开销严重拖慢仿真与 debug 周转，而现有 verbosity 控制手段要么在消息构造后才过滤、要么依赖仿真器特定 TCL、难以跨层级复用。ARM 提出 EVM：通过 opaque class extension 将 evm_layer 注入继承链，把消息划分为 build/header/detail/item/report 五类并分别设 verbosity，配置存于组件本地对象，按 group/type/instance/FHN 四级哈希 registry 匹配；verbosity 描述符为外部 JSON，经 DPI-C 调用 yyjson 解析，并在消息构造之前完成过滤。案例显示一名验证工程师半天内即可将子系统级环境接入 EVM，并在三家最大仿真器厂商中的两家上验证通过；利用运行时触发 verbosity 提升的 debug rerun 在选定用例中获得最高两个数量级加速，且免除重编译。该方法向后兼容、可渐进推广，与团队大规模 UVM 环境的日志治理和回归提效需求高度契合。

问题

在垂直复用的大型 UVM testbench（子系统/系统级，含数十至数百个 predictor、checker、agent）中，缺乏既用户友好又支持垂直复用的 verbosity 控制方案：block 级环境的日志在集成级成为噪声，uvm_report_catcher/callbacks 等过滤发生在消息构造之后带来显著性能损耗，继承或第三方组件各自实现过滤机制难以统一，仿真器特定 TCL 控制游离于验证代码库之外难以复用，导致配置成本高、日志噪声大、仿真性能下降、debug 周转慢。

方法

EVM 以 opaque class extension（参数化虚类 evm_layer#(type WRAPPED_T)）注入目标类与其父类之间的继承链，利用 SystemVerilog 构造函数执行顺序保证在任何 UVM phase 前完成 EVM 初始化，不改动父类且保持 factory type_override/inst_override 兼容；消息按 build/header/detail/item/report 五类分别设 verbosity，由宏从组件本地 evm_comp_config 配置对象实时读取，实现动态 verbosity 控制；组件在 build_phase 注册到 group/type/instance name/FHN 四个基于哈希的 registry；verbosity 描述符为外部 JSON 文件，经 DPI-C 调用 yyjson（ANSI-C）解析，scope 字符串用 xxHash/md5sum 哈希后匹配，规避仿真器字符串关联数组的性能问题；verbosity 检查发生在消息构造之前，从源头消除字符串替换、I/O 等开销；公开 API 支持运行中按仿真时间或事件触发加载新描述符，实现 debug 时 verbosity 动态提升。

关键结果

一名验证工程师在不到半天内将 ARM 一个子系统规模 testbench 完整接入 EVM，并为两个复杂组件添加 EVM verbosity 宏作为 proof-of-concept

改动代码已在三家最大仿真器厂商中的两家仿真器上运行测试，验证了跨仿真器可行性

在选定 debug 用例中，通过运行时触发 verbosity 提升（错误发生前以近似 UVM_NONE 的静默 verbosity 运行），获得最高达两个数量级的仿真加速

外部 JSON verbosity 描述符消除了 verbosity 调整的重编译需求，提升 debug 周转时间

强制字符串哈希后运行时间指标保持一致、不受字符串长度影响（此前某些仿真器对层级路径字符串仅取前几个字符生成哈希键，碰撞导致以秒计的性能损失）

创新点

区别于 uvm_report_catcher/callbacks 等在消息构造后过滤的方案，EVM 在消息构造前完成 verbosity 检查，从源头消除无效消息的构造开销；区别于仿真器特定 TCL verbosity 控制，EVM 以可纳入版本库的 JSON 描述符提供可移植方案，且除 FHN 条目外可在 unit 与 integration 层级间直接复用；通过 opaque class extension 实现对既有 UVM 类层次与 factory override 零侵入的渐进式推广，并与 ARM 已有的 item/object verbosity escalation 方法保持正交。

Enhanced Verbosity Methodology

Gergő Vékony，József Mózer

ARM，匈牙利布达佩斯

gergo.vekony@arm.com，jozsef.mozer@arm.com

摘要 - 本文提出一种面向通用验证方法学（UVM）环境的增强详细度方法学（EVM），旨在解决大型垂直集成测试平台中控制报告详细度所面临的易用性与可扩展性挑战。EVM 支持在运行时动态更新消息详细度，通过在消息构造之前对其进行过滤，降低日志噪声并提升仿真性能。该方法借助一种不透明的类扩展技术，将 EVM 层注入类继承链中，在不破坏现有 UVM 层次结构的前提下，实现了渐进式推广与向后兼容。

EVM 将消息按用途划分为若干类别（build、header、detail、item 和 report），将各组件的详细度设置存储于本地配置对象中，并维护以组件组、类型、实例名和完整层次名为键的集中式注册表。详细度设置由外部 JSON 描述文件提供，并通过 DPI-C 进行解析，同时采用哈希标识符以实现高效匹配和稳定的仿真器性能。案例研究显示，该方法在一个子系统规模的环境中得到了快速采用，具备跨仿真器可行性，并通过仿真期间触发的详细度升级改善了调试周转时间。

I. INTRODUCTION

在电子设计自动化（EDA）行业中，每年都会多次发布新工具，这些工具由日益复杂的 IP 与系统开发所驱动，提供增强的调试与验证能力。围绕设计和测试平台（testbench）划分的新范式不断涌现，编码指南描述了面向性能的解决方案，人工智能（AI）辅助工具也越来越多地承担常规任务。然而，进展明显较为缓慢的一个领域是软件与其用户之间的接口和通信。无论是用户手册、日志记录与反馈选项，还是图形界面，显而易见的是，用户体验（UX）往往并非最高优先级。

这个问题在验证中尤为突出，因为描述激励与观测结果的文本输出通常被存储在日志文件中并进行搜索。通用验证方法学（UVM）[1] 提供了多种控制显示内容的方式：全局详细度阈值、按组件的详细度设置以及报告服务器定制。控制这些设置的方法有很多（包括各仿真器厂商提供的特定功能）；然而，一种既对用户友好又适合垂直复用的解决方案尚未得到广泛采用。

在单个（通常是单元级的）测试平台中，这可能不是一个大问题；但在更高的集成层次上，它就成了一项重大挑战，因为系统或子系统测试平台可能包含数十乃至数百个预测器（predictor）、检查器（checker）和代理（agent）。在这类环境中，要配置各组件使其提供足够的信息，同时既不严重拖累性能、也不让日志充斥噪声，可能需要投入大量精力。理想情况下，每个单元级验证环境都应提供一种抑制自身消息的机制；但更常见的情况是，由于复杂性或时间限制，这一机制并未实现。

对于继承的或第三方组件而言尤其如此：其所有者可能持有不同的构想、使用自己的过滤机制、依赖特定的 UVM 报告服务器实现，甚至拥有一个处理这些问题的外部框架。尽管如此，验证假设、证明块级错误在集成层次上不可观测、或将集成层次的失败追溯至块级副作用等实际需求依然存在；因此，仍然非常需要一个解决方案。

在增强详细度方法学（EVM）中，我们采用了一组带类型参数化的 UVM 扩展组件以及一个轻量级（基于句柄的）组件注册表。我们定义了一种 JSON 描述符格式，可按组、类类型、实例名或完整层次名（FHN）为组件指定详细度设置。由于该描述符无需编译，而是在运行时进行解析/处理，用户可以快速地重新运行仿真并细化设置。我们还提供了辅助宏，用于从每个组件的本地配置对象中获取特定类别的详细度值，从而实现动态详细度控制。为降低查找和比较开销，我们采用字符串哈希进行匹配。后续章节将对这些特性进行更详细的描述。

II. EVM PARADIGMS

如引言中所述，增强详细度方法学（EVM）的动机在于提供一种动态控制基于通用验证方法学（UVM）的验证组件详细度取值的方法。为实现这一目标，我们定义了以下一组范式，这些范式在 EVM 的设计与实现过程中为我们提供了指导。

A. Dynamic Rollout

在任何项目中，最大的难题之一就是引入一组会以某种方式影响其代码库或层次结构的基础性变更。有时，由于不可预见的副作用或所需的变更数量，这样做并不可行；有时甚至根本无法实现，因为某些代码可能必须保持冻结状态。此外，SystemVerilog 也不允许多重继承，因此向继承链中的类之间添加功能可能并非易事。

幸运的是，[2] 中描述的不透明类扩展（opaque class extension）方法可以克服这一问题，它为 EVM 解决了若干障碍。该方法允许我们将一个类注入到目标类与其父类之间的继承链中，从而使 EVM 功能对目标类及其所有派生类均可用。它还依赖于 SystemVerilog 的构造函数限制（见 [3] 第 8.7 节 Constructors 和第 8.15 节 Super），即父类的构造函数保证先于派生类执行。这使我们有机会在目标类的任何代码执行之前为其完成 EVM 的设置，其中包括所有 UVM phase。

我们的实现还无需创建并维护一整层类来将不同组件纳入 EVM，不透明方法使得仅凭单个类定义即可向任何 UVM 组件注入功能成为可能。由于 EVM 是在 UVM 之上新增的一层选项，它是透明的，并保持了向后兼容性。因此，EVM 可以在各个组件上逐步推行，甚至在单个组件内部，详细度类别也可以渐进式地实现。

出于数据分离的考虑，EVM 会为所有支持 EVM 的类实例化一个配置对象，以便在本地封装所有设置、标志和详细度取值，而不会污染其派生类的内容，也不会引入需要从集中式注册表或数据库中查找取值的问题。在未提供详细度描述符（verbosity descriptor）的情况下，EVM 可以使用 EVM 包中定义的默认值，或者可以通过 EVM 公共 API 调用直接从验证平台设置组默认值。

B. Convenience

无论一种方法学在技术角度上多么出色，如果其应用及其局限性没有被精确定义，或者它过于繁复而难以部署或日常使用，它都将归于失败。出于这一原因，我们选择 JSON 作为 EVM 默认的详细度描述符格式，因为它基于文本、与版本控制兼容、易于阅读、属性顺序不敏感，并且未来可以轻松扩展。我们曾讨论过为详细度描述符实现一个额外的命令行处理器，但由于工程师倾向于将那些（通常）复杂的参数存储在其他笔记类应用中，因此最终选择引导他们采用基于文件的方法。

消息详细度可以通过四个粒度层级进行设置，范围从组（group）、类类型（class type）和实例名（instance name）等宽泛类别，到特定的完整层次名（full hierarchical name，FHN）。由于详细度更新将遵循这一粒度顺序，因此很容易制定出规则，例如抑制 EVM_AGENTS 组成员的所有消息，同时让某个特定 agent 或从同一类实例化的若干 agent 保持在详细度限制之上。

详细度描述符可以在不同的垂直层级之间移动和复用，因为除 FHN 条目之外，它们都可以被直接复用。尽管如此，同一份 JSON 可以同时包含针对单元级和集成级 testbench 的 FHN 设置，因为在当前环境中找不到的 FHN 将被简单地忽略。

为简单起见，JSON 解析和字符串哈希是通过 UVM 的 DPI-C 调用借助开源库完成的，因此无需任何 SystemVerilog 实现。虽然可能需要将 C 代码编译加入编译流程，但由于所使用的是稳定的库，它们也可以以预编译目标文件的形式分发。

A. Filtering of Messages

当子系统级或系统级 testbench 由块级环境构建而成时，通常有两个方面会出现问题：报告消息的冗余度（verbosity）和覆盖率的评定，因为二者都是从各自来源的角度完成的。属于 UVM_LOW 或 UVM_HIGH 类别的内容在更高的集成层级上可能并不成立，而且很难区分哪些是有用的、哪些看似无用。有一些方法可以过滤掉那些只会带来噪声的消息，例如使用 uvm_report_catcher 和各种回调函数。为此，可能需要某种消息统一性，以便在回调的 ID 或 MSG 字段中进行匹配。如果未实现此类解决方案，则该组件可能会被完全抑制掉。

过滤还带来了性能问题，因为消息过滤是在消息创建之后、打印之前进行的。在更高的垂直层级上，不仅 RTL 和验证组件的数量会增加，其代价高昂的操作——例如字符串替换、I/O 活动等——也会随之增多，这会显著降低仿真性能。因此，当务之急是设法提出一种能够在消息创建之前就将其过滤掉的解决方案，以使计算资源的使用尽可能接近最低水平。这正是将 EVM 实现为一种动态冗余度修改方法的动机，其中冗余度检查发生在消息创建之前。

此外，一种与 [4] 中所述且已在 ARM 使用的基于 item/object 的冗余度升级方法相正交的解决方案，似乎是恰当的选择。

B. Message Categories

通用验证方法学（UVM）作为一个框架，完全没有规定应如何使用报告宏。如何制定规则或指南来标记重要消息、并将其与鲜有用处的消息区分开来，完全由工程师自行决定。诸如通过 message ID 或 VERBOSITY 字段加以区分的方法可能较为常见，也可能通过实现一个配置变量来守护 uvm_sequence_item 派生类的 sprint()。无论采用哪种方法，似乎都需要在任何组件中设置不同的重要性层级。

在 EVM 中，引入了消息类别（message categories），为用户提供一种模糊的、高层次的分类，用以标记某条给定消息的意图。在验证环境生命周期或使用过程的不同阶段，不同的消息似乎各有其价值；例如，build 和 connect 阶段所提供的反馈，在完成初始调试和实例化模式设置之后便迅速失去价值。同样，在某些情况下，查看某个 predictor 的函数调用顺序可能是有价值的，而实际的预测消息或精确数值则不然。

为此，我们引入了 build、header、detail、item 和 report 这一组类别，并为它们各自设置了独立的冗余度级别。借助这一实现，可以将某一给定类别完全静音，同时使其余消息保持原封不动，交由 report catcher 的回调函数进行最终过滤。有了这五个类别，就可以将 build 和 cleanup 阶段的消息与 run 阶段的消息区分开来，并提供了根据重要程度和长度进一步细分 run 阶段消息的选项。如有需要，将来还可以添加更多类别，因为各类别的冗余度值是通过一个简单的宏从本地配置对象中读取的。

C. Local Configuration Objects

由于 EVM 需要跟踪那些在处理冗余度描述符时需要被更新的 EVM 感知组件，我们采用了一个集中式的句柄注册表，其中的句柄指向各 EVM 配置对象。通过这一实现，我们将原本从集中式数据库中查找冗余度值的性能开销——这种查找在仿真过程中会发生很多次——转换为了配置对象和一个句柄所带来的内存开销，同时保留了从注册表自身遍历其内容的能力。这一实现保证了更新和查找都能快速而高效地完成。

为了进一步削减计算开销，我们实现的不是一个，而是四个注册表：分别基于组件的组、类类型、实例名称以及完整层次化名称。这在 EVM 的实现和调试启动过程中带来了好处；同时它还减少了冗余度更新调用期间所需的注册表遍历次数。

D. String Hashing

使用字符串哈希而非字符串本身，是 EVM 实现层面的一种选择，其依据是在三家最大的仿真器厂商的仿真器上所做测试的结果。在某些情况下，某个仿真器决定将字符串直接作为字符串使用，而不是对它们施加某种内部哈希处理。此外，在若干情形中，只有字符串的前几个字符被用来生成关联数组键的哈希，由于层次化路径名的特性，这导致了大量的哈希冲突。实验表明，这一决策取决于数组中最长字符串的长度，并且它对查找和比较性能有严重影响，这种影响在运行时间上以秒计、可被测量出来。虽然这看起来只是一个小麻烦，我们还是决定在所有情况下都强制执行字符串哈希。这使得运行时间指标非常一致，与所使用的字符串长度无关。

B. EVM Layer Implementation

IV. EVM ROLLOUT AND IMPLEMENTATION

F. DPI Layer

增强详细程度方法学（EVM）的直接编程接口（DPI）层由两个不同的部分组成：一个作为描述符解析器的接口，另一个提供对哈希算法的访问。

我们选择了一个广为人知且经过测试的开源 JSON 解析器 yyjson [5]，该解析器以 ANSI-C（C89）编写，并针对 x86-64 和 AArch64 两种架构均提供了完善的实现，从而消除了可能出现的跨平台和编译器兼容性问题。在哈希算法方面，我们为 xxHash [6] 的 32 位和 64 位版本以及 GNU Coreutils [7] 的 md5sum 提供了接口。基于测试和性能剖析结果，我们得出结论：与使用原始字符串相比，在某些情况下，对于某些仿真器而言，使用哈希值可能具有一定优势（见第 III/D 节），但从仿真的角度来看，各哈希算法之间的实际性能差异微不足道。对于我们的使用场景而言，所有现代哈希器都能提供可忽略不计的碰撞风险。

G. JSON Descriptor Format

yyjson 库并不强制要求任何特定的 JSON 格式，它仅提供解析能力。因此，我们为详细程度描述符（verbosity descriptor）定义了一种简单的 JSON 格式。

下面给出了一个详细程度描述符的伪代码示例：

<!-- EVM 详细程度描述符格式 --> [ { <!-- scope_type 枚举为 {group, name, full_name, type} --> "scope_type": 1, "scope": "amba_axi_env", <!-- verbosities 为 [build, header, detail, item, report] --> <!-- 注意：此处抑制除 header 类型之外的所有内容 --> <!-- 注意：100 对应 UVM_LOW，600 高于 UVM_DEBUG --> "verbosities": [600, 100, 600, 600, 600] } ]

该描述符由 yyjson 解析，scope 字符串则由与 SystemVerilog 侧相同的哈希器算法进行处理。所得的结构体通过 DPI-C 传回 SystemVerilog，并根据其 scope_type 被推入 evm_layer_globals 的更新队列。

还可以进行进一步的改进，修改该格式以允许 scope_type 和 verbosities 的取值使用枚举字符串而非整数。

VI. CONCLUSIONS

在本文中，我们提出了一种方法学，用于克服在不同垂直集成层级的测试平台（testbench）中处理通用验证方法学（UVM）冗余度（verbosity）这一复杂任务。尽管该方法学是在 ARM 内部验证环境中开发和评估的，但所提出的方法学与工具无关，可适用于任何基于 UVM 的验证流程。我们展示了增强冗余度方法学（EVM）的一种实现，该实现在以跨仿真器形式对冗余度设置进行动态更改方面被证明是成功的概念验证，同时与不具备 EVM 感知能力的 UVM 组件保持了完全的向后兼容性。我们已提供证据表明，它可以轻松推广到更大规模的验证项目中，并且不会干扰复杂的基于 UVM 的类层次结构及其 uvm_factory 覆盖。此外，它有助于消除不必要的消息创建，从而提高仿真效率。

外部存储的冗余度描述符（verbosity descriptor）被证明是缩短调试周转时间的有效解决方案，因为该实现消除了重新编译的需求。已有结果表明，这些描述符可以在单元级与集成级环境之间共享，并可安全地纳入代码仓库中。尽管特定于仿真器的基于 TCL 的冗余度控制提供了灵活的运行时控制，但它们通常位于验证代码库之外，难以在不同环境之间复用。EVM 通过提供一种可移植的、受源码控制的方法学来管理跨垂直集成层级的冗余度，从而解决了这一局限。这种方法的便利性和部署简易性得到了设计与验证工程师的认可。虽然当前的实现似乎已足以满足日常使用，但我们目前正在探索引入支持子串匹配的哈希算法，以扩展冗余度描述符的能力。

我们希望这项工作能对验证工程师有所帮助，并有助于推动关于设计验证中人机交互的更广泛讨论。
