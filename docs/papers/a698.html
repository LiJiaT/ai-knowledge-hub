Large Language Models are Built-in Autoregressive Search Engines

大语言模型是内置的自回归搜索引擎

简介

论文探究能否不训练任何检索模型，仅靠提示让现成 LLM 直接充当检索器。针对双编码器稠密检索中 query 与文档交互浅、自回归搜索引擎（DSI/SEAL）训练成本随候选文档规模激增这两大痛点，作者提出 LLM-URL：用少量 (query, URL) 对作为 in-context 示例提示 GPT-3 直接生成 Wikipedia URL，经正则抽取、HTTP 实时抓取、切分与 BM25/DPR 排序过滤后交给 reader 作答。关键结论是：few-shot 下生成 URL 对应文档近 90% 含正确答案，文档 Recall@1 在 WebQ/NQ/TriviaQA 上显著超过 BM25、Contriever 等基线，且免训练、可实时获取最新文档；但在 NQ 端到端 QA 上落后 DSI/SEAL，并存在幻觉 URL、偏好高频实体、抓取慢等可靠性问题。对团队而言，这是'LLM 即检索器'这一 RAG 替代范式的早期实证，其 few-shot 检索提示设计与可靠性分析对知识库问答的检索策略选型有直接参考价值。

问题

双编码器稠密检索器（如 DPR）对 question 与 document 独立编码，二者只有浅层交互，且压缩为单一稠密向量易丢失细粒度信息；自回归搜索引擎（DSI、SEAL）通过直接生成文档标识实现深度交叉注意力，但训练成本随候选文档数量急剧上升，小模型又难以胜任 question 到标识的映射，且不同检索任务需求不同、希望仅凭少量示例即可泛化。论文要验证：能否不经过任何训练，仅凭人类指令与少量示例让现成 LLM 直接生成文档标识（URL）完成检索。

方法

提出 LLM-URL：以 'Which m Wikipedia URLs would have the answer?' 为指令并拼接 URL 前缀以约束生成格式，在 few-shot 设置下附加 d=10 个 (query, URL) in-context 示例（zero-shot 则不给示例），提示 GPT-3 text-davinci-003（greedy 解码、temperature 0）自回归生成 m 个 Wikipedia URL；用正则表达式从生成文本中抽取合法 URL 并丢弃多余信息，通过 HTTP GET 实时抓取文档，切分为 passage 后用 BM25 或 DPR 等打分函数排序，保留 top-n 作为 reader（InstructGPT）的输入上下文生成最终答案。关键设计是直接复用互联网上已存在的文档标识 URL，而非 DSI/SEAL 那样新造标识并微调模型，因此无需训练检索模型、无需构建标识到文档的映射索引。

关键结果

few-shot 提示下，LLM 生成 URL 对应的文档近 90% 包含开放域问题的正确答案（WebQ）

文档检索：zero-shot 文档 Recall@1 相对最强基线在 WebQ/NQ/TriviaQA 分别提升 20.4%/11.2%/13.2%，few-shot 进一步扩大到 24.9%/12.8%/16.7%

passage 检索（配 BM25 排序）：zero-shot Recall@1 相对提升 16.2%/5.3%/1.1%，few-shot 为 16.8%/11.8%/6.3%；但对比 DSI/SEAL，Recall@1 落后 8.8%（zero-shot）/3.1%（few-shot），Recall@10 落后约 18.7%/18.4%

端到端 ODQA（配 InstructGPT reader）：zero-shot 相对最佳基线 WebQ +13.3%、TriviaQA +1.3%、NQ -39.5%；few-shot WebQ +16.9%、TriviaQA +2.3%、NQ -37.4%

生成 URL 的有效率在 m 从 1 增至 10 期间保持高于 68%，但随 m 增大而下降，边际收益递减

常见实体问题的 recall 远高于不常见实体；LLM-URL 检索到的文档平均约 10k 词，远超 Wikipedia 文章平均值 644 词

创新点

与 DSI、SEAL 等需微调模型生成新造文档标识的自回归搜索引擎不同，LLM-URL 完全免训练，直接利用冻结 LLM 的 in-context 能力生成互联网上既有的标识 URL：URL 含页面标题语义且格式固定，实验显示生成 URL 的召回显著优于让模型生成 Wikipedia 标题；URL 可经 HTTP 请求直接换取文档，无需训练模型或建索引做标识到文档的映射；自回归生成使每个新 URL 以先前已生成的 URL 为条件，检索到的文档相互互补而非独立选取；文档实时抓取，天然支持时间敏感查询，而 Contriever 需重新编码、DSI/SEAL 需重训才能跟上文档更新。
