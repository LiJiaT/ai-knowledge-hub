StructGPT: A General Framework for Large Language Model to Reason over Structured Data

StructGPT：支持大语言模型（LLM）在结构化数据上进行推理的通用框架

简介

LLM 在处理知识图谱、表格、数据库等结构化数据时，因数据格式与 schema 特殊且数据量庞大，难以将全部记录放入 prompt 并准确理解。StructGPT 提出 Iterative Reading-then-Reasoning（IRR）框架：把结构化数据封装为黑盒系统，设计专用接口（如抽取邻居关系、三元组、列名、子表、DB schema）负责精确高效的数据访问与过滤（reading），LLM 则专注基于接口返回的信息进行推理（reasoning），通过 invoking-linearization-generation 流程多轮迭代逐步逼近最终答案或可执行 SQL。在 KGQA、TableQA、Text-to-SQL 三类任务共 8 个数据集上，相比 zero-shot 直接使用 ChatGPT，WebQSP Hits@1 提升 11.4%、TabFact 准确率提升 4.2%、Spider 执行准确率提升 4.7%，并可媲美全量数据监督微调方法。对团队而言，其'接口负责精确读、模型专注推理'的解耦范式，以及大结构化数据下的上下文裁剪与线性化策略，可直接借鉴到知识库问答与数据问答类 Agent 的工具接口与上下文设计中。

问题

LLM 在预训练中较少接触结构化数据（知识图谱、表格、数据库）的特殊格式与 schema，难以准确表示和理解这类数据；且结构化数据量往往庞大，无法将全部数据记录放入输入 prompt。论文要解决的是：在不微调模型的前提下，以统一范式支持 LLM 基于多类型结构化数据完成问答与推理任务。

方法

提出 Iterative Reading-then-Reasoning（IRR）框架 StructGPT：将结构化数据视为黑盒系统，为 KG、表格、数据库分别设计专用接口（如 Extract_Neighbor_Relation、Extract_Triples、Extract_Column_Name、Extract_Columns、Extract_SubTable、Extract_Table&Column_Name、Extract_Tables_Information），由接口完成精确、高效的数据访问与过滤以缩小搜索空间；随后通过 invoking-linearization-generation 流程，把接口返回信息线性化为文本 prompt，配合两类提示模板（'Here are [Y]. Which [X] are most relevant...' 的证据选择类与 'Based on [Y], please generate [Z]...' 的答案/SQL 生成类）驱动 LLM 生成；多轮迭代调用接口直至得到最终答案或可执行 SQL。

关键结果

相比 zero-shot 直接使用 ChatGPT，WebQSP（KGQA）Hits@1 提升 11.4%，TabFact（TableQA）准确率提升 4.2%，Spider（Text-to-SQL）执行准确率提升 4.7%

在 KGQA、TableQA、Text-to-SQL 三类任务共 8 个数据集上，zero-shot 与 few-shot 设置下均显著提升 Davinci-003 与 ChatGPT 的性能，可媲美全量数据监督微调方法

zero-shot 不使用 KG 时，ChatGPT 在 WebQSP 达 61.2（对比 GraftNet 66.4），Davinci-003 达 48.3（对比 KV-Mem 46.7），说明 LLM 自身具备一定知识，但在 MetaQA-2hop/3hop 等多跳任务上表现不佳，需要 KG 增强

错误分析：WebQSP 上选择错误占 74%，Spider 上推理错误占 62%，WikiSQL 上格式、选择、推理错误分布相对均匀

使用 8 月最新版 ChatGPT 的补充实验显示，方法在 WebQSP、WTQ、Spider 三个任务上仍带来一致提升，表明方法具有鲁棒性

创新点

据论文所述，这是首个以统一范式支持 LLM 在表格、KG、数据库等多类型结构化数据上推理的工作。与 UnifiedSKG 等需要微调模型参数且受最大输入长度限制、无法处理大规模结构化数据的方法不同，StructGPT 无需训练，并通过接口操作海量结构化数据；与只针对单一结构化数据类型的已有 LLM 方法相比，其接口设计加迭代流程具有跨数据类型与跨任务的通用性。
